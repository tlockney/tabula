# P5.6: Profiles

| Behavior | Source | Packet |
| --- | --- | --- |
| A profile is a named set of shared settings that many devices can be assigned to; every paired device belongs to exactly one profile, the built-in empty one unless another is assigned | F-MGT-02 | P5.6 |
| A device's effective value for a key a profile covers is the profile's value, or a per-device override when one is set; every other key keeps the device's own value | F-MGT-02, ADR 0035 item 2 | P5.6 |
| Identity, connection and hardware keys are never shared by a profile: a request that carries one, alone or inside a larger save, loses that key with a per-key reason and keeps the rest | F-MGT-03, ADR 0035 item 8 | P5.6 |
| A new profile covers no keys at all, so nothing room- or panel-specific is shared until the user adds it | F-MGT-04, ADR 0035 item 9 | P5.6 |
| Editing a key a profile covers for one device records an explicit per-device override, shown marked in the Tabularium; later profile saves leave that key alone, and clearing the override applies the profile's value again | independent design, ADR 0035 items 1-4 | P5.6 |
| Saving a profile writes only the covered values that differ from what each member holds, as one settings revision per device; a member that is offline receives it when it reconnects | F-MGT-02, F-MGT-01, ADR 0035 item 2 | P5.6 |
| Profile names are unique ignoring case, at most 64 characters, and the built-in empty profile's name is reserved; a save adds at most 32 profiles | independent design, ADR 0002 `PROFILE_NAME_MAX`, `PROFILE_MAX` | P5.6 |
| The built-in empty profile is permanent and read-only: it covers no keys, so a device in it keeps its own settings | F-MGT-02 | P5.6 |
| Deleting a profile moves its devices to the built-in empty profile and changes none of their settings; the devices keep the values they last received | F-MGT-02 | P5.6 |
| The Tabularium's Profiles section lists profiles with their devices, creates, renames and deletes them, picks covered groups and keys one by one, previews what a save would change, assigns a profile from each device page and offers a sync-now action | F-MGT-02 | P5.6 |
| The drift report lists members whose reported settings revision differs from Home Assistant's copy (how far behind, whether online, when last seen), members that intentionally differ through an override, and members whose app predates a key the profile covers | independent design, ADR 0035 item 7 | P5.6 |
| Drift compares revisions rather than values, because the tablet never uploads its settings document, and Home Assistant keeps the last revision a device reported so an offline member can still be compared | independent design, ADR 0035 item 7 | P5.6 |
| A settings key the app's schema cannot take is held the usual way: the member applies what it knows, agrees on the revision, and the drift report names the key it could not take | F-UPD-08, ADR 0035 item 7 | P5.6 |
| `tabula.assign_profile` puts the targeted tablets in a profile, named by name or id and applied straight away, and `tabula.sync_profile` applies a profile to its members or to the targeted tablets | F-MGT-02, ADR 0035 item 6 | P5.6 |
