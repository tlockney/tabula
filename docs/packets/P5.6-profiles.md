# P5.6 — Profiles: shared keys, diff, push and drift

Side: build   Tier: deep   Depends on: P5.3 (the settings store and role tags from P1.5/P3.1 are merged)
Verification: ci
Issue: #154
Status: ready

## Why

Households with several tablets repeat the same settings by hand. F-MGT-02 defines profiles as named partial settings documents many devices can share, with a strict rule that identity, connection and hardware keys never travel (F-MGT-03), and a default that new profiles start without room- and panel-specific keys (F-MGT-04). This packet adds the server-side profile layer, the effective-value computation, the push path that reuses the settings revision machinery, a diff before pushing, a drift report, and the panel editor. It is the packet where "shared" stops being a schema annotation and becomes an enforced permission.

It also has to settle F-MGT-02's open question (what happens when a covered key is edited for one device). The packet starts with that ADR because the answer shapes the store, the push and the UI.

## Do

1. **ADR first.** Decide F-MGT-02's open question in a new ADR before writing the store: per-device override, refusal, or overwrite on next sync. The FEATURES recommendation is an explicit per-device override with a visible marker; the ADR must also say how a profile push treats an overridden key, what the panel shows, and how an override is cleared. Also record the drift definition (below) and the assignment storage (HA-side, never sent to the device; the device only ever receives effective values).
2. **Profile store.** A `ProfileStore` in the integration (HA `Store` in `.storage`, loaded with the hub), holding named partial documents of `shared`-role leaves only, plus per-device assignment. The built-in empty profile is permanent and read-only and covers no keys. Names are unique; removing a profile moves its members to the empty profile. The store validates on save with the schema's own validator (types, bounds, patterns), and rejects any key whose role is not `shared` — including a request that smuggles `identity`/`connection`/`hardware` keys inside the payload — with a per-key reason. A profile with no keys is valid.
3. **Effective values.** For a device assigned to a profile, the effective document is: per key, the override if the ADR allows one and it is set, else the profile's value when the profile covers that key, else the device's own value. Only covered keys are ever pushed; uncovered keys stay exactly as HA stored them. Pushing is one revision and one `set_settings` per device (the existing path), and only keys that differ from the device's current effective value are sent.
4. **Sync behaviour.** Saving a profile queues a push to online members; offline members are marked and receive it at their next registration / subscription reconcile. Deleting a profile does not rewrite members' settings (it only moves them to the empty profile); the UI says so. A device that is behind on schema version keeps held keys as today (plan 5.4). Every push is a normal revision bump, so a profile save never bypasses `async_set_settings`'s validation and the settings entities refresh.
5. **Diff and drift.** A diff between a profile and one member (or all members) lists covered keys with the profile value, the member's current value and whether it would change. The drift report lists members whose reported revision does not equal HA's stored revision (how many revisions behind, online/offline, last seen), members with an override shadowing a profile key, and members whose device schema version predates a covered key. The device never uploads its settings document, so drift is revision-based, not value-based; the ADR says this plainly so nobody expects a value comparison the protocol cannot provide.
6. **Panel.** A Profiles section: list with member counts, create/rename/delete, a group picker with per-key exclusion (new profiles start empty, which satisfies F-MGT-04 without a second list of "room" keys), a diff preview before saving, an assignment control on each device page, a "sync now" action and the drift report with per-member details. Keys the panel cannot share are not offered at all (the server still enforces it).
7. **Services.** `tabula.assign_profile` (device target, profile name/id) and `tabula.sync_profile` (profile id, optional device target) per F-MGT-02, with the same enforcement and results as the panel commands.
8. **Panel commands.** `tabula/panel_profiles` (list + assignments), `tabula/panel_profile_save`, `tabula/panel_profile_delete`, `tabula/panel_profile_assign`, `tabula/panel_profile_diff`, `tabula/panel_profile_sync`, `tabula/panel_drift` — all admin-only, all validating shapes and device/profile existence.
9. **Tests.** Python (`integration/tests/test_profiles.py`): role refusal (identity, connection and hardware keys each refused, including inside a larger payload), name uniqueness, empty-profile permanence, delete moves members, effective values with and without overrides, diff output, push only differing keys with one revision, offline member pushed after reconnect, held keys for an older schema, drift for a stale revision and for an override, no secret or credential in any payload, admin-only. TypeScript: profile editor, group picker/exclusions, diff preview, assignment, drift rendering, error display. Mock end-to-end with two devices: a profile save changes both, an offline one catches up on reconnect.
10. **Manual check.** With two `mockdevice` instances paired, create a profile, assign both, save it, watch both apply; take one offline, change the profile, see it listed as drifted, bring it back and see it catch up. Paste what was observed.

## Out of scope

- Backup/restore and import/export (F-MGT-05).
- Credential sharing toggles (F-MGT-02 mentions sharing each kind of credential): schema v3 has no credential setting in the shared layer, so there is nothing to share yet; the role rule already excludes connection keys.
- Profile inheritance, nesting or ordering.
- Pushing a profile to a device's unshared keys, or making a profile cover runtime state.
- Updating the settings schema for profiles (assignment lives in the profile store, not in the device settings document).
