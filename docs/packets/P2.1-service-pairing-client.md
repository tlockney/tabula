## Do

1. Foreground service, boot receiver, pairing screen (code and device_id), nonce and claim, Keystore-backed credential storage, persisted device_id.
2. WebSocket client: auth, register with versions, command loop, ACKs, backoff, heartbeat.
3. Battery, charging, connectivity and app-version sensors.
4. Start `docs/DEVICE.md`: ADB provisioning (install, `pm grant`, `appops set` for WRITE_SETTINGS, deviceidle whitelist, `dpm set-active-admin`) as a script in `tools/device/`, plus ADB recovery steps.

### What was built

- `android/ha/` (new plain-JVM module, the plan section 6 `ha` module): the
  device-side TLP client. `PairingClient` (code + nonce attempt, pair/claim
  with PROTOCOL 2's terminal handling), `TokenRefresher` (margin refresh,
  final `invalid_grant`/403 per ADR 0001), `Backoff` (equal jitter, PROTOCOL 7),
  `TlpClient` (auth handshake, register with versions/capabilities/full state,
  subscribe, command loop with typed-args validation and exactly one result
  per command, coalesced state pushes at STATE_MIN_INTERVAL, the HA ping
  heartbeat with PONG_TIMEOUT, superseded handling, reconnect with backoff),
  and OkHttp HTTP/WS transports. Every timing value comes from ADR 0002 via
  `core` Constants.
- `android/app/`: a `connectedDevice` foreground service (ongoing
  notification, Wi-Fi wake lock, START_STICKY) that pairs on request and then
  keeps the session up; a boot receiver that starts it after boot when
  paired; a pairing screen (HA address entry, then code + device ID);
  Keystore-encrypted credential storage (`allowBackup=false`); persisted
  UUIDv4 device_id; battery / charging / network / Wi-Fi RSSI / app-version
  state; `set_settings` (with the per-connection revision floor),
  `restart_app`, `reload`, `clear_cache` handlers. `coreLibraryDesugaring`
  enabled per ADR 0008.
- mockdevice: a `serve` command (in-process test server on a chosen
  host/port, announcing `LISTENING <url>`) and `/test/confirm`,
  `/test/command`, `/test/report` HTTP hooks, so the JVM test can drive the
  server the way the Python tests do.
- `tools/device/`: `provision.sh` (install + ADB grants), `check_p21.sh`
  (the scripted hardware acceptance), `ha_query.py` (HA device-registry
  query over its WebSocket API). `make android-apk` builds the debug APK.
  `docs/DEVICE.md` written (provisioning, hardware check, recovery,
  security notes).
- `PROVENANCE.md`: rows for the pairing screen, credential storage, the
  foreground service, the sensors and revocation handling.

### Deviations / decisions

1. **Plain-view UI, not Compose.** The pinned compileSdk 34 toolchain
   (ADR 0008) predates current Compose runtimes; the P2.4 overlay should add
   the compileSdk ADR and bring Compose in with it.
2. **New `:ha` Gradle module** (plain JVM) for the client state machine, per
   the module layout in plan section 6, so it unit-tests without the
   Android SDK.
3. **mockdevice grew a `serve` command and `/test/*` hooks** — test
   infrastructure for the JVM-against-Python-server test the packet invited
   ("if it's practical"). It is practical and runs in CI.
4. **`reload` / `clear_cache` ACK as no-ops** until the dashboard arrives
   (P2.2); the packet's command list only requires the loop and ACKs.
5. **`make android-apk` added** (not part of `make check`): provisioning
   needs a buildable APK; the toolchain discovery mirrors
   `tools/android_test.sh`.
6. **The hardware check's entity assertions are live.** This branch was cut
   before P1.3 (entity platforms) and P1.5 (settings, events) merged; after
   merging main they are part of this PR's tree, so at hardware-verification
   time `check_p21.sh` sees battery/charging sensors and the connectivity
   binary sensor, and its entity-state output is meaningful. The HA registry
   query and the app's `connection lost` logcat line remain the primary
   scripted evidence either way.
7. **Echo Show boot observation: skipped** — P0.6 returned a provisional
   no-go (ADR 0007: no known settings-only path to ADB; every working path
   is an exploit plus bootloader unlock, which the plan excludes). Recorded
   in DEVICE.md. If the ADR's device check overturns the no-go, P2.7 owns
   the bring-up.
8. **FGS type `connectedDevice`** may hit runtime prerequisites on
   Android 14+ devices; the API 28 targets are unaffected. Noted in
   DEVICE.md for the first newer-device packet.
9. **Credential storage** is AES-GCM under an AndroidKeyStore key with
   `allowBackup=false` (plan 5.2); cleartext traffic is enabled because HA
   on the LAN may be plain http (PROTOCOL 2 threat model), and DEVICE.md
   recommends HTTPS.
10. **The pairing screen takes the HA address as a field** (not an ADB
    push): the simplest design consistent with plan 5.2 and 5.9 for this
    phase; ADB recovery (`pm clear`) is documented in DEVICE.md.
