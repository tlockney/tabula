# P3.3 — Clock faces and background image

Side: build   Tier: standard   Depends on: P3.1
Verification: hardware
Issue: #61
Status: awaiting-hardware

## Why

The P2.4 clock mode is a fixed digital face. F-SSV-08 asks for faces and options (at least digital and analog with hands) and F-SSV-09 for an optional background image from a local file or a URL, with periodic re-fetch and a darkening layer. This packet makes the clock configurable within the schema v2 keys, staying in the plain-view screensaver overlay (ADR 0013 item 1).

Note on unverified device facts: the P2.4 hardware checks (#18) have not run, so the overlay's on-device behavior (legibility at the held screensaver brightness, touch dismissal) is unobserved. The hardware part of this packet can share the same device session as #18's run; no spike is needed because nothing here depends on a device-specific capability.

## Do

1. Faces: digital (current face, now taking the v2 settings: font, weight, 12/24-hour, AM/PM marker, seconds, date line, size, colors, app-language date with system-language fallback) and an analog face with hands. Rendering is plain framework views (custom onDraw view is fine); no Compose (ADR 0013 item 1).
2. Background image (F-SSV-09): local file path or URL, decoded at panel resolution, optional re-fetch interval; a settings write always triggers a fresh load even when the value is identical (the revision change is the signal); a failed fetch keeps the previous image and retries later; a darkening layer of the configured strength keeps the face readable. The URL fetch attaches no credential to non-HA URLs and no credential at all unless a design decision says otherwise — record the choice in an ADR.
3. Modes that are not built yet keep showing the clock (ADR 0013 item 3); no change to the stand-in rule.
4. JVM tests: face-layout logic (option combinations), the image loader (fake transport: success, failure keeps previous, re-fetch interval, always-reload-on-write) — the P2.5/P2.6 fake-transport patterns.
5. `tools/device/check_p33.sh` and a DEVICE.md section, following the P2.4 check script's shape.
6. `PROVENANCE.md` rows.

## Result

**What was built**

- `android/core` (`core.screensaver.clock`, plain JVM, 20 tests):
  - `ClockLayout`: the digital face's pieces per option combination (time pattern with optional seconds, the AM/PM marker, the date line, resolved typography and colors), the analog hands' angles, the analog texts, the date-locale fallback (app language when the app ships a translation, system language otherwise), and the background source classification (URL vs local path).
  - `ClockBackgroundController`: the background's state machine — load at start, show on success, failed load keeps the previous image and retries at the next re-fetch tick (or the next write, when no interval is configured), the re-fetch interval applies to URLs only, every `applySettings` call orders a fresh load identical source or not, blank source clears, stop ignores late answers.
- `android/app`:
  - `ScreensaverView`: the clock now renders the v2 settings (F-SSV-08) — the digital face (font family, weight, 12/24-hour, AM/PM marker, seconds, date line, size percent, text and background colors) and an analog dial (custom `onDraw` view, ADR 0013 item 1 allows it) with the marker and date under the dial. The time follows `hour_24` from the settings (a behavior change from P2.4's system-format face, ADR 0018); the date line uses the app language with the system fallback.
  - `ClockBackgroundEngine`: carries the background rules out (F-SSV-09) — decode at panel resolution through the P3.8 decoder, URL fetch over the P2.5 media fetch (no credential, ever; ADR 0001 item 5 and ADR 0018), a cache file deleted after the decode, show-then-release ordering, generation-counted supersession (a superseded load is released, never drawn), the darkening layer at the configured strength, and the F-SSV-02 pause with the window. 6 tests.
  - Reload-on-write wiring: `TabulaCommands` bumps a `TabulaStatus.settingsRevision` state on every applied `set_settings`; the activity collects it and re-applies the clock settings whenever a face is drawn (any clock-showing mode, including the ADR 0013 stand-in), so writing the same background source still reloads it (F-SSV-09: the revision change is the signal).
- Docs and scripts: ADR 0018 (the schema's open answers: analog option mapping, date line shape and language, no credential on the fetch, retry-later without a new constant, interval for URLs only, reload-on-write, the font-weight axis across minSdk 24); the `CLOCK_TIME_BASE_SP`, `CLOCK_DATE_BASE_SP` and `CLOCK_DIAL_FRACTION` rows in ADR 0002; PROVENANCE rows for F-SSV-08/F-SSV-09; `tools/device/check_p33.sh` and a DEVICE.md section.
- Modes not built still show the clock (ADR 0013 item 3); the stand-in rule is unchanged (no code change needed — the stand-in renders through the same face path).
- Deviation from the brief: none. Item 1's "plain framework views (custom onDraw view is fine)" is followed to the letter; the analog face is the custom view.
