# P5.5 — Screenshots and command buttons

Side: build   Tier: standard   Depends on: P5.2 (P3.13's CI part is merged; its hardware part is not required here)
Verification: ci
Issue: #153
Status: in-review

## Why

The device page's Activity tab: what the tablet shows right now and the small set of actions HA already exposes for it. P3.13 built the capture path, the authenticated upload view, the image entity, the capture button and the last-capture timestamp; `button.py` already has reload, restart, clear cache, go home and capture, each gated by capability; the hub already refuses a command to an offline device with a clear error. This packet adds no protocol surface — it wires the panel to those entities and shows their real outcomes, including the failure text, instead of a spinner that never resolves.

## Do

1. **Screenshot panel.** The Activity tab shows the device's image entity (`image.*`): the latest capture, the placeholder when the screen was off (F-MGT-07), or a "not captured yet" state when the entity has no image; the last-capture timestamp from its sensor; a caption built from the device's reported state (`screen_on`, `screensaver_active`/`screensaver_mode`, `current_page`), refreshing when state changes arrive; and a capture button that presses the existing `button.*_capture_screenshot` and shows the pending state until the entity's state changes (with a timeout that reports "still running" rather than hanging).
2. **Command buttons.** Render the device's button entities by their translated names (reload, restart app, clear cache, go to the start page, capture screenshot), each disabled with a reason when the entity is unavailable (offline device, capability missing) — the panel must not offer a command the integration will refuse. A press shows running, then the outcome: success, or the error text HA returned (command timeout, failed code, offline). No optimistic state changes on the device's behalf.
3. **Safety.** Restart and clear-cache are configuration actions and are visually separated from the benign ones (capture, reload, go home); clearing the cache is presented as affecting the dashboard's stored data, matching its HA description. No confirmation dialog is invented for restart; HA's own entity has none. The panel adds no new services and calls only what the integration already exposes.
4. **Live updates.** The tab follows the entities through `hass.states` (entity state subscription, no polling): a capture completes in HA, the image and timestamp update; a device going offline disables the buttons and marks the screenshot as from the last connection.
5. **Tests.** Vitest, with a fake `hass` and a fake entity registry: screenshot states (image, placeholder, none), caption per screen/screensaver/page combination, capture pending → image change, capture timeout, buttons rendered per capabilities, unavailable buttons disabled with reasons, offline device, service error shown verbatim, restart separated from benign actions. A small integration test asserts the payload from P5.2 carries the entity ids the panel relies on for a capability-limited device (no screenshot capability → no image/button ids).
6. **Manual check.** With `mockdevice` paired, the Activity tab shows the placeholder after a screen-off capture, the capture button updates the image and timestamp, and an offline device disables the buttons. Paste what was observed.

## Out of scope

- The capture path itself, the upload view or the placeholder (P3.13).
- Automatic re-capture after a screen-state change (F-MGT-07 says "may"); the caption covers the state without extra commands.
- Parameterised commands (navigate, notify, screensaver with arguments): those stay HA services in the developer tools until a later packet defines an action runner.
- A log or event timeline on this tab (P5.4's Logs tab is separate).
- Any screenshot history; HA keeps one image per device.

### Deviations

- **The manual check was not run.** This packet is `Verification: ci` and this
  machine runs no HA instance, so there is no mock-device observation to paste
  and no HA version to name, as P5.1 and P5.2 recorded. The payload contract is
  covered by `integration/tests/test_panel_activity.py` against real HA
  components over the real WebSocket surface, and every rendering and press path
  by `panel/src/activity.test.ts` (26 cases) in jsdom with a fake `hass`. What no
  test here can show is the bundle rendering inside a live frontend against a
  paired mock device.
- **The placeholder and a stored capture cannot be told apart.** ADR 0014 says
  so: a screen-off capture drops the stored image but the image entity still
  moves its timestamp, so `hass.states` cannot say which image is being served.
  The tab therefore shows the image with its capture time and puts the device's
  reported screen state in the caption, and shows the placeholder note only when
  the entity holds no image at all (nothing captured yet, or the file is gone).
  It never claims a capture was screen-off when the entities do not say so.
- **Command buttons are classified by entity id, with the name as a fallback.**
  The registry builds ids from translated names, so the settled set arrives as
  `_reload_dashboard`, `_go_to_start_page`, `_restart_app`, `_clear_cache` — not
  `_reload`/`_go_home`. The suffix match handles those, and a renamed entity
  falls back to the words in its name ("Reload dashboard").
- **A capture's pending state ends on the image entity, not the button.** HA
  sets a button's own state to the press time *before* the entity runs, so the
  button changing says nothing about the capture. The tab watches the image
  entity's state instead, and the service call's outcome for errors.
- **The still-running notice is the panel's own constant** (20 s, ADR 0002):
  longer than `COMMAND_TIMEOUT` so HA's own error text usually arrives first,
  shorter than `SCREENSHOT_TIMEOUT` so a slow capture reports in.
- **No confirmation is invented for restart or clear cache**, per the packet:
  HA's own button entities have none. They are only visually separated, with the
  clear-cache note stating that it removes the dashboard's stored data.

### Open questions for the architect

- The still-running notice keeps the press pending and still shows HA's later
  outcome; if a follow-up wants a cancel affordance, it needs a decision on what
  cancelling means for a capture already in flight on the tablet.
- `hass.states` is read from the `hass` the frontend hands the panel; if a later
  packet needs per-entity subscriptions (rather than whole-state pushes), the
  `HomeAssistant` contract in `types.ts` is the one place to widen.
