# P0.4 — TLP v1 and constants

Side: build   Tier: deep   Depends on: P0.3
Verification: ci
Issue: #7
Status: in-review

## Why

The Tabula Link Protocol is the contract between the integration, the mock device and the Android app. Its golden fixtures are what all three test against.

## Read first

- `AGENTS.md`
- `docs/PLAN.md` section 5 and 7.1 (P0.4), section 8
- `docs/decisions/0001-ha-platform.md`
- `docs/FEATURES.md` (if P0.2r is done; not a dependency)

## Do

1. Write `docs/PROTOCOL.md`: pairing and claim, register/registered (protocol and schema versions, capabilities, settings revision), state deltas, command frames with `command_id`, result frames, `set_settings`, events, log subscription, the HTTP screenshot upload, reconnect/backoff rules and the version compatibility rules (plan 5.4). Each frame type gets a JSON Schema definition.
2. Write `docs/decisions/0002-constants.md`: protocol timeouts, backoff bounds, rate limits and the Phase 1–2 behavior defaults.
3. Add a golden fixture for every frame type in `schema/fixtures/`.
4. Write `tools/validate_frames.py` and wire it into `make check`.

## Out of scope

- Integration, mock device or Android code.
- Settings schema (P0.5).

## Done when

- `make check` runs `tools/validate_frames.py` and it validates every fixture in `schema/fixtures/` against the schemas in `docs/PROTOCOL.md`.
- Every frame type in `docs/PROTOCOL.md` has at least one fixture.

## Hand back

Result section: frame type list, fixture count, validator output.

## Result

Changed:

- `docs/PROTOCOL.md`: TLP v1 (pairing and claim with threat model, credential use, WebSocket session and keepalive, tolerant receivers and capability negotiation, register, subscribe, state deltas, commands with `command_id`, settings revision rules, results, events and their HA bus mapping, logs and redaction, superseded connections, screenshot upload, errors, reconnect and backoff, versioning, fixture layout).
- `docs/decisions/0002-constants.md`: every constant PROTOCOL.md names, every schema bound, and Phase 1–2 behavior defaults, each with its reasoning.
- `schema/tlp-v1.schema.json`: one `$defs` entry per frame type, listed in `x-tabula-frames`; per-event `data` schemas.
- `schema/fixtures/tlp/v1/`: 45 valid fixtures, 24 must-fail fixtures in `invalid/`, with `invalid/EXPECTED.json` naming where each must fail.
- `tools/validate_frames.py` + `tools/tests/test_validate_frames.py`: checks the frame list against `$defs` both ways, checks formats, checks each invalid fixture fails where expected. `make frames` added to `make check`; `jsonschema[format-nongpl]` added to the dev dependencies.
- `docs/PLAN.md` 5.1: screenshot path updated to match.

Deviations:

- The brief says the schemas live in `docs/PROTOCOL.md`. They live in `schema/tlp-v1.schema.json`, which PROTOCOL.md references by `$defs` name, so code (mock device, integration, Kotlin codegen) loads one file rather than parsing Markdown. Same pattern as the settings schema (plan 5.6).
- Plan 5.1's screenshot upload becomes `POST /api/tabula/screenshot` with no device ID in the path; the device is resolved from the token (connection binding). Plan 5.1 is updated in this PR.
- The device sends HA's `ping` command for keepalive (`APP_PING_INTERVAL`, `PONG_TIMEOUT`), because HA's own pings are invisible to the app. `ping` and `pong` are frame types.

Review changes: an independent review asked for forward compatibility (open capability names, accepted capabilities in `register_result`, tolerant receivers), origin-safe `navigate` and `play_media` (HA-relative paths allowed), format checking, a cross-connection settings revision rule, superseded-connection handling, `409 already_pending` for a competing pairing request, protocol version read before validation, per-event data schemas, redaction rules, screenshot upload tied to a pending command, and recorded bounds for every schema limit. A second review asked for the plan's screenshot path, the remaining bounds, removal of the unused `unknown_device` error and the register state wording. After FEATURES.md landed, a third round widened the enums to match it (notification levels F-NTF-02, screensaver modes F-SSV-05, media actions F-MED-01), added the enum-extension rule to section 8, and sourced the superseded-socket claim. All are in.

PROVENANCE: no user-visible behavior lands here. P0.5 adds `PROVENANCE.md` rows for the behavior defaults when it makes them settings.
