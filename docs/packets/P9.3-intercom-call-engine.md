# P9.3 — Intercom call engine in the Android app

Side: build   Tier: deep   Depends on: P9.1
Verification: hardware
Issue: #141
Status: awaiting-hardware

## Why

The app must place, ring, answer, carry and end a call. ADR 0028 settled the library, the audio route and the guards; the spike (`android/spike-intercom/`) proved the audio path on two Fire HD 10 Plus units but is a debug-only app with a throwaway relay. This packet moves the engine into the production app behind the TLP frames from P9.1. It is the largest Phase 9 packet; keep the engine behind an interface so the UI packets and the unit tests never touch real audio.

## Do

1. Add `io.github.webrtc-sdk:android:125.6422.07` to the app (the version ADR 0028 measured), registry only. Build one ABI per APK or an ABI split (arm64-v8a, armeabi-v7a) so the APK does not carry four libraries; record the resulting APK sizes.
2. Define a `CallEngine` interface (start, answer, decline, end, state flow, call info: who, mode, direction, started time) with a fake implementation for tests, and a `WebRtcCallEngine` implementation. Nothing outside the engine imports WebRTC types.
3. Engine rules from ADR 0028: audio only, Opus, mono capture from `VOICE_COMMUNICATION`, software AEC/NS/gain on, empty ICE server list (host candidates), `INTERCOM_CONNECT_TIMEOUT_S`, `INTERCOM_RING_LIMIT_S`, hard limit `INTERCOM_CALL_LIMIT_S` that ends the call by itself. A call runs in a foreground service holding a partial wake lock and a Wi-Fi high-performance lock, released on end. Tones and any sound the intercom makes during a call use `USAGE_VOICE_COMMUNICATION`.
4. Listen-only: a device without a working microphone declares `intercom_listen` only and answers with a `RECV_ONLY` transceiver and the record path disabled. `intercom_talk` is declared only while `RECORD_AUDIO` is granted at registration; follow how P7.1 reports the microphone state.
5. Broadcast: receivers play and keep their microphone closed; the sender sends only. The receiver's reply (a two-way call back to the broadcaster) is requested through the UI packet and starts through the normal call path.
6. TLP wiring: handle `intercom_ring`, `intercom_signal`, `intercom_end` commands; emit `intercom_answer`, `intercom_decline`, `intercom_signal`, `intercom_ended`, `intercom_start_request` and the `intercom_state` key. Exactly one result per command (PROTOCOL 4.5).
7. Guards: no auto-resume (a service or boot restart starts in idle and reports idle); a call ends if the TLP connection to HA drops for longer than a constant-defined grace (reuse an existing reconnect constant, do not invent one; if none fits, hand back with a proposal); an end from HA stops the call in every state.
8. Microphone ownership with the wake-word detector (P7.1): the detector releases the microphone when a call that uses it starts and re-acquires it after the call. A unit-testable arbiter, not a device test.
9. Unit tests with the fake engine and a fake peer-connection factory: the state machine for every transition, each guard, the limit timers on a fake clock, listen-only selection, the capability declaration rules, the microphone hand-off, the TLP handlers. `make check` and the existing Android test target must pass.
10. `docs/provenance/P9.3.md`: independent design.

## Result

Status: awaiting-hardware. ### What was built

Item by item, as the packet numbers them:

1. **The dependency and the APK shape.** `io.github.webrtc-sdk:android:125.6422.07`, the version ADR 0028 measured, added to `:app` from Maven Central with no extra repository. The app now builds one debug APK per v1 ABI (`armeabi-v7a`, `arm64-v8a`) and no universal APK; `tools/android_build.sh` prints the files the build produced and their sizes (see below). The service also declares `MODIFY_AUDIO_SETTINGS`, which WebRTC's audio device module needs to set the communication route.
2. **`CallEngine` and its two implementations.** The interface, `CallInfo` (`callId`, mode, direction, who, start time, whether the call captures), the state flow and the event stream are in `:core` (`net.lockney.tabula.core.intercom`). `CallMachine` is the state machine and is the only implementation of the transitions; `FakeCallEngine` is the scripted fake the wiring's tests use; `WebRtcCallEngine` is the production one — the machine with `WebRtcPeerFactory`, the Android clock, the main-looper scheduler and the call's locks. `WebRtcCallEngine` is the only file in the app that imports WebRTC: `TabulaCommands`, `IntercomManager` and the service see `CallEngine` only. The connection itself is a `CallPeer` behind a `CallPeerFactory`, which is what makes the state machine JVM-testable without audio.
3. **Engine rules from ADR 0028.** Audio only; the library's Opus default; mono capture from `VOICE_COMMUNICATION` through `JavaAudioDeviceModule` (mono is the module's default, which is what the spike measured; nothing sets it explicitly) with hardware cancellation and suppression requested and WebRTC's software echo cancellation, noise suppression and gain made explicit (`googEchoCancellation`, `googNoiseSuppression`, `googAutoGainControl`); an empty ICE server list, so host candidates only; `INTERCOM_CONNECT_TIMEOUT_S` from the answer or from this device's own answer, `INTERCOM_RING_LIMIT_S` from the ring, and `INTERCOM_CALL_LIMIT_S` (`Constants`, still provisional at 300 s) from the moment the call is up — the answer for a callee, the start for a caller, the ring for a broadcast. The engine takes a partial wake lock and a Wi-Fi high-performance lock when a call begins, ringing included, and releases both when it ends. No tone is played by this packet: the ring and the answer tone belong to the screen (P9.4) and auto-answer (P9.5), and anything they play must use `USAGE_VOICE_COMMUNICATION` as ADR 0028 measured.
4. **Listen-only.** A device answers with `RECEIVE_ONLY` and the record path disabled when it cannot talk; its `CallInfo.usesMicrophone` is false, so the microphone arbiter never lets a call like that take the detector's capture. `intercom_talk` is declared only while `RECORD_AUDIO` is granted at registration, re-read every session the way P7.1 reports the microphone, and `intercom_listen` is always declared because every device has a speaker.
5. **Broadcast.** A broadcast rings a receiver straight into `in_call` with a `RECEIVE_ONLY` connection and no answer, exactly as P9.1's mock does; the sender goes to `broadcasting` with a `SEND_ONLY` connection and sends only. The receiver's "call back" button is P9.4's and starts through the ordinary call path. See open question 2: with the merged integration, a broadcast's signaling is not relayed, so no receiver can actually join one yet.
6. **TLP wiring.** `IntercomManager` handles `intercom_ring` (ok, or `busy` when a call is up), `intercom_signal` (ok, or `invalid_args` for a call this device is not in, P9.1's mock rule) and `intercom_end` (always ok; another call's id changes nothing), and turns each engine event into exactly one frame: `intercom_answer`, `intercom_decline`, `intercom_signal`, `intercom_ended`, `intercom_start_request`. It publishes `intercom_state` on every state change and the registration carries it; the key always exists because `intercom_listen` is always declared (PROTOCOL 4.4's gate). `TabulaCommands` answers one result per command, as the client requires of every handler.
7. **The four guards**, each enforced in the machine and each covered by a test:
   1. *An explicit action only.* Only `start` (the device's own action or a schedule) and `ring` (an HA command) create a call. Nothing runs on a timer that could begin one; a new engine is idle and stays idle while the clock advances ten minutes.
   2. *A hard limit.* `INTERCOM_CALL_LIMIT_S` ends the call with reason `limit` from every state, broadcast included.
   3. *An end from HA in every state.* `intercom_end` takes the call down from ringing, connecting, in call, broadcasting and a playing broadcast, with one result and one `intercom_ended`. While the link is down that command cannot arrive, so the call ends at the disconnect grace instead: `PONG_TIMEOUT_S`, the app's existing "this connection is dead" interval, reused rather than invented. `BACKOFF_MAX_S` was the other candidate and was rejected as too long: a call feeding back would then run a minute after HA had lost the ability to stop it.
   4. *No resume.* A call lives only in the machine's fields; the engine is constructed inside the service, so a service or process restart starts idle and registers idle. A test proves a second machine has no call.
8. **Microphone ownership.** `MicArbiter` sits between `WakeWordGate` and `WakeWordMonitor`: a call that captures closes the detector's capture and the detector re-acquires the microphone when that call ends, if it still wants it. It counts a call as holding the microphone only once the call is up and only when that call captures, so a ringing call and a broadcast being played leave the detector listening. The transitions are unit-tested.
9. **Tests.** 49 new JVM tests: 26 for the machine, 6 for the arbiter, 1 for the gate and arbiter together, 2 for the start frame's target rule, 14 for the wiring, plus the capability rules in the wiring's tests. See below.
10. **Provenance.** `docs/provenance/P9.3.md`, all rows independent design.

### Decisions taken here (in the packet's gift)

1. **The disconnect grace is `PONG_TIMEOUT_S`.** The packet says to reuse an existing reconnect constant, and this is the app's existing answer to "the connection is dead": HA's own liveness window. `BACKOFF_MAX_S` (60 s) was rejected because guard 3 is about how long HA cannot stop a call, and a minute of unattended audio is exactly what the guard exists to prevent. If 10 s proves too tight against this house's Wi-Fi, the constant is ADR 0002's to change.
2. **The engine is in `:core` and the WebRTC adapter in `:app`.** `:core` gains `kotlinx-coroutines-core` (state flow and event channel) but no Android and no WebRTC, so every transition is a JVM test. `WebRtcCallEngine` is a one-screen adapter: machine + `WebRtcPeerFactory` + `AndroidCallScheduler` + `AndroidCallLocks`.
3. **The call's own locks are separate from the service's.** The service has held a lifetime Wi-Fi high-performance lock since P2.1; the call takes its own pair on begin and releases them on end, so "a call holds both locks" is a property of the call and is testable, rather than something inherited by accident.
4. **The hard limit starts when the call is up.** For a callee that is the answer, for a caller its own start, for a broadcast the ring - ADR 0002's wording and P9.1's mock. ADR 0028's stricter reading ("answered or not") would start it at the ring for a two-way call too; that is a protocol-visible choice HA cannot see either way, and the packet's own reference (the mock) is this one.
5. **A decline reports `intercom_decline` and no `intercom_ended`.** P9.1's mock does the same, and P9.2's `_async_declined` ends both sides from the decline.
6. **The caller learns the answer from the relayed SDP.** No frame tells a caller its callee answered (HA's `tabula_intercom_answered` is a bus event, not a command), so the caller arms its connect timeout when the relayed answer arrives and treats ICE connected as "up". This is the P9.2 open question 1's shape from the device side and is recorded below.
7. **Candidate payloads are JSON.** `intercom_signal`'s payload is "the candidate's own text"; a candidate needs its `mid` and `mLineIndex` to be applied, so the field carries `{"mid":…,"mline":…,"sdp":"candidate:…"}`. A payload from another implementation is ignored rather than allowed to end the call, and the 4 KiB `INTERCOM_SIGNAL_MAX_BYTES` bound is far above both this and an offer.
8. **`intercom_state` is always present.** `intercom_listen` is declared unconditionally, so PROTOCOL 4.4's gate is satisfied; the registration carries the key as `idle` because the engine is idle at start.
9. **Ties are broken toward reporting.** A connection that cannot be created, an SDP failure and ICE failure all end the call with reason `error` and an `intercom_ended`, rather than leaving a call up that cannot carry audio. A call that ends while the link is down cannot report; the next registration's `intercom_state: idle` is the record.

### Deviations and gaps

1. **An HA-started call still cannot reach its own caller's engine** (P9.2 open question 1). The merged protocol rings only the callee with the call id; nothing tells the caller that the call exists, so its engine stays idle and ignores the callee's relayed answer. Device-started calls work end to end: the device mints the id, HA rings the callee, the answer comes back through `intercom_signal`. Implemented as merged PROTOCOL 4.5 describes; no protocol change was made here.
   **Proposal:** one additive, `intercom_listen`-gated command that tells the caller — `intercom_start` (`call_id`, `mode`, `peer_name`/`callee_name`), or the same thing as a `ring` with a `role` field. HA sends it to the caller when it starts a call, before or with the ring to the callee; the caller's engine opens the offer exactly as it does for a device-started call. The alternative (relaying the callee's answer to a caller that has no call) cannot work, because the caller has no id to attach it to.
2. **A broadcast has no signaling path in the merged integration** (found while wiring item 5; PROTOCOL 4.5 says signals are relayed unchanged, and P9.2's `_async_signal` returns early for `MODE_BROADCAST`). With that early return, no sender's offer and no receiver's answer ever crosses the relay, so a broadcast would ring, report `in_call`, and carry no audio until the hard limit. The device side implements what PROTOCOL says — a `SEND_ONLY` sender and `RECEIVE_ONLY` receivers that answer an offer if one arrives — and nothing was changed in the integration, which is P9.2's.
   **Proposal:** remove the broadcast early return in `_async_signal` so broadcasts relay like calls, and decide the topology in the same ADR: with one PeerConnection per peer, the sender needs one connection per receiver, which also needs `intercom_signal` to say which device sent it, because v1's frame carries only `call_id`, `kind` and `payload` and a sender cannot tell two receivers' answers apart. Until then a broadcast is a single-receiver call at best.
3. **A stale `intercom_state` HA has no call for** (P9.2 open question 2) is left to the device guards, as the protocol and the mock expect: a reload drops HA's calls and sends nothing, and a tablet in one then ends it by its own hard limit (or the disconnect grace, if the link went with it), reporting idle at the next register. Nothing is guessed at, and nothing is resumed.
4. `INTERCOM_CALL_LIMIT_S` is used through `Constants` at its provisional 300 s; changing it is ADR 0002's and the owner's, and no code here hard-codes it.
5. **No ring tone and no call screen.** The packet puts the screen in P9.4 and auto-answer in P9.5; this engine has no on-screen entry point yet, so nothing in the app can start or answer a call until P9.4 lands. That also gates the device part below.
6. `WebRtcPeerFactory` creates a `PeerConnectionFactory` and a `JavaAudioDeviceModule` per call and disposes them on end, the spike's shape. One factory per process would be cheaper; it was not changed because the spike's measurements are the only ones this project has, and a call is at most one per five minutes.

### Device part (hardware verifier, owner-scheduled)

Not run. The steps, for whoever runs them once P9.4's screen exists (without it there is no button to answer with, and the caller side of an HA-started call has no engine until open question 1 is decided):

1. Build `app-arm64-v8a-debug.apk` from this branch, install it on two paired Fire HD 10 Plus units, and confirm both register with `intercom_listen` and `intercom_talk`.
2. On tablet A's intercom screen, call tablet B; answer on B; confirm both show `in_call`, that speech is audible both ways, and that `tabula_intercom_answered` and `tabula_intercom_ended` fire.
3. During the call, call `tabula.intercom_end` from HA; confirm both tablets stop within a second and report `idle`.
4. Leave a call up and confirm it ends by itself at `INTERCOM_CALL_LIMIT_S`, and that a ring nobody answers ends at `INTERCOM_RING_LIMIT_S` as a missed call.
5. With the wake word enabled, confirm `wake_word_active` goes false when the call is answered and true again when it ends.
6. Repeat 2 with `RECORD_AUDIO` revoked on B: B must answer listen-only, hear A, and never send.

### Review (PR #171) fixes

The review at `e6a90c5` found five items and one note. Each is addressed here; nothing about the frame design, the constants or the guards changed.

1. **Candidates that arrive while the callee rings are no longer dropped** (medium). The machine now keeps them beside the pending offer and hands them to the connection when it is created, so the caller's host candidates - which leave within milliseconds of its offer, long before anyone answers - reach the peer. `candidates that arrive while ringing reach the peer on the answer` sends two while `ringing` and one after, and asserts all three arrive in order.
2. **The capture bit has one owner** (medium; a microphone could stay open). `WakeWordGate` no longer decides from its own cached capture state: it reports its *decision* whenever that decision changes, and reports a stop whenever capture was last asked for, whichever owner closed or reopened the microphone in between. The arbiter stays the only thing that opens and closes capture. `WakeWordGateArbiterTest` runs the review's sequence - a call takes the microphone, a playback inside the call drives the gate's stop and an unsatisfiable start, the call ends and capture returns, the switch goes off - and asserts the microphone ends closed. `WakeWordGateTest`'s refused-open case now expects the stop that comes with the decision flip; closing a microphone that never opened is a no-op.
3. **The connect deadline now runs from this device's own answer** (low-medium), whether or not the offer has arrived: `answer()` arms it, and the existing guard keeps it from being armed twice. `an answered call whose offer never arrives still times out` covers the offer-never-arrives path; `an answered call that never connects times out` keeps the offer-first one.
4. **The provisioning path follows the per-ABI build** (low, but it is the install path). `tools/device/provision.sh` now resolves `app-arm64-v8a-debug.apk` and falls back to `app-armeabi-v7a-debug.apk`, so an unargumented run works again, and `docs/DEVICE.md` names the per-ABI file.
5. **The start request's target rule is enforced, not assumed** (nit). `EventFrame.intercomStartRequest` refuses a call with neither or both targets and a broadcast with either, and `IntercomManager.start` refuses the same shapes before the engine is asked, returning `StartOutcome.InvalidTarget`. Two tests cover the frame, two cover the manager, and P9.4's screen cannot put an illegal shape on the wire in the meantime.
6. **The mono note** is corrected in item 3 above: mono is the audio device module's default, which is the shape the spike measured.

### Open questions for the architect

1. The caller-side frame in deviation 1 — a command that tells a device it is the caller, and its name.
2. Broadcast signaling and topology in deviation 2 — the relay exception and the missing sender id, and whether a broadcast is one call per receiver or a new frame shape.
3. Whether the disconnect grace should be `PONG_TIMEOUT_S` (10 s, chosen) or a value of its own in ADR 0002, now that a call depends on it.
4. Whether the hard limit should run from the ring (ADR 0028's "answered or not") rather than from the answer (ADR 0002, the mock, decision 4 here).
