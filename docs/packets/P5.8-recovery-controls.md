# P5.8 — Recovery-page controls

Side: build   Tier: deep   Depends on: the Phase 4 recovery-page packet (issue #22); P5.3
Verification: hardware
Issue: #156
Status: blocked

## Why

Plan 5.9's recovery page is the most sensitive surface on the tablet: re-pointing the HA URL can send the dashboard to a hostile server, so it is off by default, needs a PIN with no default, and turns itself off after a timeout. Phase 4 builds the page, the PIN check, the rate limit and the settings/command surface behind it. This packet adds the only convenient way to operate it — the Tabularium's controls — and, more importantly, the rule that the PIN never becomes HA data: it is sent to the device and hashed there, and the panel can only show whether one is set.

The packet is blocked because the page and its commands do not exist yet. It must not invent a second recovery mechanism or a PIN that lives in HA's Store.

## Do

1. **Use Phase 4's surface, do not add one.** The page's enable, timeout and rate limit are Phase 4's; this packet consumes its settings/commands and the capability it declares. Read the Phase 4 packet first and follow its names. If its surface is missing something the panel needs (for example a status the panel must show), hand back to the architect rather than adding a parallel command.
2. **PIN handling.** The PIN is set and cleared through the Phase 4 command, never through the settings document: HA must not persist it in `.storage`, the config entry, diagnostics, backups or logs, and the panel must not keep it in component state after submit. The command carries it once over the authenticated device connection; the device hashes and stores it; the result says only set/not set. If Phase 4 implemented the PIN as a setting instead, stop and hand back — that design would put the PIN in HA's backups.
3. **Panel controls.** A Recovery section on the device page: the enable switch (off by default, disabled with an explanation until a PIN is set), a write-only PIN field with set and clear actions (type once, confirm, cleared from the form immediately; no "show" toggle), a timeout selector from the Phase 4 constants, the page's port from PROTOCOL, a status line (enabled/disabled, PIN set/unset, remaining time when the device reports it, lockout state when reported), and a warning that enabling it exposes a LAN-reachable page that can re-point the device and that HA should be HTTPS (F-MGT-10). The section explains the ADB escape hatch without documenting the whole runbook.
4. **Behaviour.** Enabling without a PIN is refused by the device; the panel disables the action and explains why. Changing the PIN while the page is enabled takes effect for the next attempt and is reported as such. Disabling takes effect immediately. A cleared PIN disables the page (no default PIN). A command failure (offline device, refused, timeout) shows the error text and leaves the switch in its previous state.
5. **Audit.** Every enable, disable, PIN set/clear and timeout change from the panel is recorded where the integration already records device commands (the log ring / event path), with the device and the action, never the PIN. Diagnostics for the device show set/unset only.
6. **Tests.** Python (`integration/tests/test_panel_recovery.py`): admin-only and unknown device; enable refused without a PIN; PIN set/clear sends the command and stores nothing (assert the settings store, entry data and diagnostics contain no PIN string); the timeout value is validated at the Phase 4 bounds; status mapping; offline and failed commands leave state unchanged; no PIN in HA's log records. Mock device: implements the Phase 4 recovery commands, including a lockout and a timeout. TypeScript: write-only field, confirm-once flow, switch disabled without a PIN, timeout options, status and lockout rendering, error paths, no PIN retained in state.
7. **Hardware check.** `tools/device/check_p58.sh` and a `docs/DEVICE.md` section: enable from the panel and reach the page from a LAN machine; log in with the PIN set from the panel; a wrong PIN locks out per Phase 4; the timeout turns the page off; clearing the PIN stops it; and a grep of HA's `.storage` and the device diagnostics finds no PIN. Paste the output.

## Out of scope

- The recovery page, the PIN hashing, the rate limiter and the lockout (Phase 4).
- Enabling the page over ADB (Phase 4's runbook).
- Changing connection keys from the panel. The recovery page is the LAN path for that; HA's options flow and services remain the normal route.
- A password manager or PIN generation; the panel takes what the user types.
- The HA HTTPS decision (plan 10), beyond the warning text.
