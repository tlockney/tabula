### Deviations / decisions

1. **Two HA-down options, both scripted and documented** (the brief allowed
   either): option A stops HA itself through verifier-provided
   `TABULA_HA_STOP_CMD`/`TABULA_HA_START_CMD` (the tablet's network stays
   up — the truer test, and an actual HA restart); option B, the default,
   cuts the tablet's route with `svc wifi disable`, the `check_p21.sh`
   fallback. The script prints which path ran.
2. **The offline screensaver start is evidenced device-side** (backlight at
   the screensaver level plus the verifier's eyes) because HA and its
   switch are unreachable during the outage; offline start/stop events are
   dropped by design (ADR 0013), so the HA-side evidence is the switch
   state refreshed from device state at recovery (step 7 gates on `off`
   after the offline dismiss).
3. **The screensaver-brightness gate defaults to 20 %** (the ADR 0002
   default) with a `TABULA_SAVER_BRIGHTNESS_PCT` override, because the
   setting cannot be read from HA mid-outage.
4. **The backoff-reset check (step 8) severs the link with a Wi-Fi blip**
   rather than a second HA stop: the device-side backoff is what is under
   test, and one HA boot cycle already costs minutes. The gate is
   re-registration within 30 s of Wi-Fi returning; a counter that had not
   reset after the outage's attempts would re-dial at up to
   `BACKOFF_MAX` (60 s, ADR 0002).
5. **The reboot step is skippable** (`TABULA_SKIP_REBOOT=1`) for reruns.
6. **Offline-code review of the merged Android code: two small defects
   found and fixed; nothing larger.** The two were the `awaitCall`
   late-response close and `MediaManager.close()`'s missing monitor (both
   above). The fetch race has a new JVM test that fails with the fix
   reverted; the close() monitor is not deterministically testable on the
   JVM, so it is covered by review and the existing close-path tests.
   Reviewed and found sound: the reconnect loop
   catches everything but revocation/rejection and always backs off
   (`TlpClient.run`), the backoff reset is marked after
   `BACKOFF_RESET_AFTER` of stable registration (`Backoff.markStable`,
   unit-tested; step 8 checks it on hardware), no path crashes the process
   when HA is unreachable, the dashboard WebView is kept through CONNECTING
   phases and nothing reloads it on disconnect (`MainActivity.render`,
   `DashboardView`), offline event queues are bounded with drop-oldest
   (ADR 0002 buffers), and screen control and the screensaver run on the
   service scope, independent of the connection.
7. **No PROVENANCE rows:** no new user-visible behavior; the new ADR 0002
   rows record constants for behavior that already shipped.

### Review round (PR #53, "changes requested")

All four items addressed in `tools/device/check_p26.sh` (plus DEVICE.md);

1. **Restore on any exit (must-fix 1).** Flags record whether this script
   stopped HA (`ha_is_down_by_us`, option A) or cut the tablet's Wi-Fi
   (`net_down_by_us`, option B and step 8); `trap restore EXIT` plus
   INT/TERM traps that restore and then exit put each one back on any
   failure, Ctrl-C and normal exit, printing what it restored. The
   matching "up" calls clear the flags, so a clean run's exit trap only
   restores the settings. Verified without hardware by driving the real
   restore/flag/trap code (extracted verbatim from the script) against
   stubs: option A restores HA, Wi-Fi and settings (light to its original
   brightness, adaptive to its original state); option B restores Wi-Fi
   and settings; SIGINT restores and exits 130; a clean exit restores
   nothing. Output pasted below.
2. **The option A probe tells up from down (must-fix 2).** `ha_is_down`
   and `ha_answers` now use `curl -s -o /dev/null -w '%{http_code}'` and
   treat *any* HTTP status — 401 included, which is what HA answers on
   `/api/` without a token — as "HA answered"; only 000 (no answer at
   all) counts as down.
3. **No cutting the line adb rides on (must-fix 3).** `network down`
   (option B's fallback and step 8, in both options) first requires the
   adb transport to be USB: a `host:port` serial, or an adb devices line
   without `usb:`, fails with a message saying to use USB or option A.
   The stub run shows a `192.168.1.55:5555` adb being refused before any
   Wi-Fi command. Documented in DEVICE.md; the same latent gap in the
   older `check_p21.sh`/`check_p23.sh` is noted there too and left as a
   follow-up (they are P2.1/P2.3 artifacts).
4. **Step 2's settings changes are undone (should-fix).** The light's
   state and brightness and the adaptive switch's state are recorded
   before the first change, and `restore` puts them back through HA
   (waiting for HA to answer and the tablet to re-register, with a
   by-hand fallback message if neither returns within 240 s).

### Second review round (PR #53, "changes needed")

Reviewed at 11b1fc8, so its blocker 1 (the restore trap) was already
addressed by the first round's commit; everything else is addressed here:

1. **Blocker 1 (restore on any exit) — already done** in the first review
   round: flags, `trap restore EXIT` plus INT/TERM traps, settings
   restore; the stub-run evidence above covers it.
2. **Blocker 2 (the post-reboot registration gate).** The old step 1
   cleared logcat *after* the boot-time registration was logged, and the
   app does not re-register when the activity starts, so step 2's
   `wait_for_log "registered with HA device"` could only pass on flaky
   boot connectivity — and a skip rerun passed on the previous run's
   stale line. Fixed: the reboot path never clears logcat (the buffer is
   fresh after a reboot, so no stale lines exist and the boot-time
   registration and phase lines survive as evidence); a skip rerun clears
   the buffer up front (no fresh boot lines to preserve) and gates on live
   HA-side evidence instead: `wait_for ha_available "$TABULA_SCREENSAVER"`
   runs in both modes.
3. **Nits, all taken:** the reconnect gate now has an upper bound
   (`attempts <= 10`; equal jitter capped at `BACKOFF_MAX` yields about
   7–8 in 90 s, so a tight loop fails); `expected_level` rounds half-up
   like `ScreenController.toSystemLevel` instead of Python's banker's
   round (30 % → 77, 70 % → 179, verified); step 5 now gates that the
   backlight left the screensaver level when adaptive is off (with
   adaptive on the level is room-decided and can legitimately equal the
   screensaver level, so the verifier's answer is the gate there);
   ha_query.py takes the token from the `TABULA_HA_TOKEN` environment
   when `--token` is omitted, and check_p26.sh calls it that way (an
   argument is visible in `ps`); the airplane-mode/Wi-Fi toggle uses a
   plain if/else (shellcheck is now fully clean); the "fixed with tests"
   wording is corrected above; issue #20 carries the `awaiting-hardware`
