# P7.3 — Assist satellite entity and pipeline forwarding

Side: build   Tier: deep   Depends on: P7.2
Verification: ci
Issue: #145
Status: awaiting-review

## Why

ADR 0024: voice is a native `assist_satellite` entity in the `tabula` integration. It receives the device's PCM over the binary channel (P7.2), runs HA's Assist pipeline, and sends pipeline events and the TTS reply back. This is also the base that voice-started intercom calls (P9.6) build on.

## Do

1. `assist_satellite` platform, entity created only when the device declares `voice` (F-HA-02 pattern). Subclass `AssistSatelliteEntity`; implement `async_accept_pipeline_from_satellite` by feeding the device's PCM stream from the binary handler, start stage STT with the wake-word phrase set so HA's cross-device cooldown applies (ADR 0024 decision 3).
2. Register the binary handler per turn, send `voice_start`, unregister at turn end, on disconnect and on timeout; no leaked handlers.
3. Map `on_pipeline_event` stages to TLP: reply playback goes through the existing media path using the `tts-end` URL on the assistant audio channel (ADR 0024 decision 4); errors end the turn cleanly.
4. `ANNOUNCE` supported from the floor via `play_media` with `announce`; `START_CONVERSATION` only if the running HA has it, detected at setup by capability, not version string (ADR 0024 decision 5).
5. Entity state follows the device turn state; unavailable with the device; pipeline and wake-word selection use HA's standard satellite config.
6. Tests against the mock device with HA's harness: a full turn with a faked pipeline, wake-word phrase passed through, cooldown rejection surfaced, announce, disconnect mid-turn, handler cleanup, entity not created without the capability, two devices in parallel.
7. `docs/provenance/P7.3.md`: independent design.

## Out of scope

Android capture and playback, intercom intents (P9.6), arbitration of our own design, voice timers.

### What it does

- `assist_satellite` platform (`assist_satellite.py`), created only for a device
  that declares `voice` (F-HA-02 gating, unchanged mechanism). The entity is
  available exactly while the device is connected, like every other Tabula
  entity.
- A turn starts on the device's `wake_word_detected` (P7.1): a binary handler is
  registered on the device's connection, `voice_start` goes out with
  `start_stage` `stt` and the phrase, and the handler's PCM is handed to HA's
  pipeline through `async_accept_pipeline_from_satellite`.
- Pipeline events map onto TLP: `stt-end` stops capture (`voice_stop` `ended`,
  handler unregistered, stream closed), `tts-end` plays `tts_output.url` with
  `play_media` on the media path (ADR 0024 item 4), an `error` cancels the turn
  (HA's `duplicate_wake_up_detected` logged as the expected outcome), and
  `run-end` closes whatever is still open.
- Every exit closes the turn the same way: `run-end`, the device's
  `voice_turn_ended` (timeout/error), a superseded or closed connection, and
  entity removal. Closing is idempotent, so a turn cannot send two stops or leak
  a handler; a cancelled pipeline calls `tts_response_finished()` because HA's
  base class never reports `run-end` for it (ADR 0034 item 4).
- `ANNOUNCE` from the floor; `START_CONVERSATION` only when the running HA's
  enum has it (no version strings), with the start message played and a turn
  opened for the reply. No wake word is offered for selection: the phrase is the
  device's own model, and HA is told which one fired.
- The reply wait is bounded by `VOICE_REPLY_TIMEOUT` (ADR 0002), resolved by the
  device's `media_finished` or its `media_state` leaving `playing`.

### Constants (ADR 0002)

`VOICE_REPLY_TIMEOUT` 60 s — one new constant; the rest of the turn uses HA's
own values (chunk, cooldown, stages) or the device's turn limit (ADR 0033).

### Dependencies the HA wheel does not declare

`assist_satellite` imports HA's conversation and audio-pipeline code:
`hassil`, `home-assistant-intents`, `pymicro-vad`, `pyspeex-noise`, and on
2026.10 also `gazetteer-matcher`. The integration dev group pins them at
2026.2.3 (`integration/pyproject.toml`) and `tools/ha_matrix.sh` installs each
leg's own pins from that release's `package_constraints.txt`, so no single pin
breaks another leg (ADR 0034 item 7). The test harness now sets up the core
`homeassistant` component and the satellite's dependency chain, because the
platform is forwarded on every hub setup.

### The new tests (`integration/tests/test_tabula_assist_satellite.py`)

A full turn with a faked pipeline (phrase passed through, four 320-byte chunks
reaching the pipeline, `voice_stop` `ended`, `play_media` on the tts URL, entity
state through listening → processing → responding → idle, handler table empty
afterwards); HA's duplicate-wake-word rejection cancelling the turn with nothing
played; `announce` reaching the device as `play_media` with `announce` true;
a disconnect mid-turn leaving no handler and no current session; the device's
own timeout ending our side; no entity without the `voice` capability; two
devices running turns in parallel with independent handler tables and streams;
and a full turn against the real mock device (wake word, in-memory PCM, reply
URL, entity back to idle). No test plays or captures audio; the mock generates
its PCM in memory (ADR 0033 item 7).

### HA-version differences found

`async_internal_announce` and `AssistSatelliteAnnouncement` changed shape
between 2025.1 and 2026.2 (preannounce fields, `original_media_id`,
`tts_token`); the entity only reads `announcement.media_id`, which is stable.
`START_CONVERSATION` and `async_start_conversation` do not exist at the floor,
so the feature flag comes from the enum at import time and is absent there.

### Deviations

- No protocol change: the reply uses the existing `play_media` command, and the
  "assistant audio channel" of ADR 0024 item 4 is the device's own playback
  channel, which is Android's work (out of scope here). PROTOCOL.md is untouched.
