# P7.3 — Assist satellite entity and pipeline forwarding

Side: build   Tier: deep   Depends on: P7.2
Verification: ci
Issue: #145
Status: ready

## Why

ADR 0024: voice is a native `assist_satellite` entity in the `tabula` integration. It receives the device's PCM over the binary channel (P7.2), runs HA's Assist pipeline, and sends pipeline events and the TTS reply back. This is also the base that voice-started intercom calls (P9.6) build on.

## Do

1. `assist_satellite` platform, entity created only when the device declares `voice` (F-HA-02 pattern). Subclass `AssistSatelliteEntity`; implement `async_accept_pipeline_from_satellite` by feeding the device's PCM stream from the binary handler, start stage STT with the wake-word phrase set so HA's cross-device cooldown applies (ADR 0024 decision 3).
2. Register the binary handler per turn, send `voice_start`, unregister at turn end, on disconnect and on timeout; no leaked handlers.
3. Map `on_pipeline_event` stages to TLP: reply playback goes through the existing media path using the `tts-end` URL on the assistant audio channel (ADR 0024 decision 4); errors end the turn cleanly.
4. `ANNOUNCE` supported from the floor via `play_media` with `announce`; `START_CONVERSATION` only if the running HA has it, detected at setup by capability, not version string (ADR 0024 decision 5).
5. Entity state follows the device turn state; unavailable with the device; pipeline and wake-word selection use HA's standard satellite config.
6. Tests against the mock device with HA's harness: a full turn with a faked pipeline, wake-word phrase passed through, cooldown rejection surfaced, announce, disconnect mid-turn, handler cleanup, entity not created without the capability, two devices in parallel.
7. `docs/provenance/P7.3.md`: independent design.

## Out of scope

Android capture and playback, intercom intents (P9.6), arbitration of our own design, voice timers.
