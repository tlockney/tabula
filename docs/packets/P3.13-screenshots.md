# P3.13 — Screenshots: device capture, upload view, image entity

Side: build   Tier: standard   Depends on: none
Verification: hardware
Issue: #71
Status: awaiting-hardware

## Why

F-HA-12 and F-MGT-07's HA side: on-demand capture of the device's screen, uploaded over HTTP (PROTOCOL 5), shown as an HA image entity, with a timestamp sensor that persists across restarts. The protocol is already in place — `command_screenshot`, the `screenshot` capability and the authenticated upload view's shape are all TLP v1 with fixtures — but nothing implements them: the integration has no upload view or image platform, and the device has no capture path.

Unverified device fact: nothing has yet observed the app's window compositing on the tablet (P2.1–P2.2 hardware parts #15/#16 are still awaiting-hardware), and capture happens on the real surface. Capture of the app's own window via the standard view-capture path needs no device-specific capability, so this needs no spike — but the hardware part requires a paired, connected tablet, so it shares a device session with the pending Phase 2 checks.

## Do

1. Device capture: render the app's window (dashboard WebView and overlays alike) into a bitmap and JPEG-encode at the command's quality (bounded by the schema). Capture runs on the main thread's view tree; the encode and upload off it. Screen off at command time → `ok` with no upload, and the integration serves a placeholder image instead of a black frame (F-MGT-07); the placeholder's design (a static asset, not a black JPEG) is a small ADR note.
2. Upload: `POST /api/tabula/screenshot` per PROTOCOL 5 — bearer token, `X-Tabula-Command-Id`, body ≤ `SCREENSHOT_MAX_BYTES`; upload first, then the `tabula/result` for the command (PROTOCOL 4.6).
3. Integration: the `TabulaScreenshotView` (the pairing views' registration pattern): token → device, pending-command check (`409 no_pending_screenshot` otherwise), `403` for non-Tabula users, `413 too_large`; stores the latest image per device (media dir, not the config store; size-bounded to one image per device); the image entity serves it when the device declares the `screenshot` capability.
4. A capture button entity (candidate per F-HA-12: "candidate capture button and timestamp sensor") plus the timestamp sensor: the time of the last capture started by that action, persisted across HA restarts, untouched by ordinary image fetches.
5. The device declares the `screenshot` capability at registration.
6. Mock device: handle `screenshot` (capture → a tiny generated JPEG → upload → result) so the conformance suite covers the round trip, and the integration tests use the mock end to end: button → command → upload → image entity updated → timestamp sensor.
7. JVM tests: capture wiring against a fake view tree (screen off path, encode bounds), upload client (headers, size refusal, result ordering).
8. `tools/device/check_p313.sh` and a DEVICE.md section.
9. `PROVENANCE.md` rows.

## Result

### What was built

- Integration: `TabulaScreenshotView` (`POST /api/tabula/screenshot`, PROTOCOL 5) — device resolved from the bearer-token user, `409 no_pending_screenshot` unless `X-Tabula-Command-Id` names a still-pending `screenshot` command, `403` for non-device users, `413 too_large` past `SCREENSHOT_MAX_BYTES` (bounded chunked reads); `ScreenshotStore` keeps one image per device in the media dir; the `image` platform serves the stored capture or the bundled placeholder; a `capture_screenshot` button, a `last_capture` timestamp sensor (persisted, F-HA-12) and the image entity exist only with the `screenshot` capability (F-HA-02).
- Android: `CommandHandler.handle` is now `suspend` and takes the `CommandEvent`, so the capture (WebView draw on main, JPEG encode on a worker) and the `postBytes` upload complete before the reply is sent; the flow lives in `ScreenshotFlow` (screen off → ACK with no upload, F-MGT-07; no dashboard, no HA URL or a refused/broken upload → `failed`); the device declares the `screenshot` capability; `SCREENSHOT_JPEG_QUALITY = 80` (ADR 0002) when the command sends no hint.
- Mock device: `screenshot` command (quality validated against the schema bounds), capture → upload before `tabula/result`, screen-off skips the upload, a failed upload fails the command; the test server mirrors the upload view and now reports the upload state per device.
- Hardware check: `tools/device/check_p313.sh` and a DEVICE.md section.
- Docs: ADR 0014 (the placeholder), the `SCREENSHOT_JPEG_QUALITY` row in ADR 0002, PROVENANCE rows for F-HA-12, F-MGT-07, F-HA-02, F-HA-04.

### Deviations

1. The placeholder is a designed static JPEG (near-black slate with a muted power-off glyph, bundled in the integration), not a black frame — recorded in ADR 0014, as the packet's Do item 1 anticipated.
2. A screen-off capture does not merely "serve the placeholder next": the integration drops the stored image when a capture command completes with no upload, so the entity shows the placeholder (the Done-when behavior) and a stale screen-on screenshot never lingers as if current.
3. The mock device has no screen: it validates the `quality` hint (10–95) but returns a fixed embedded 16x16 JPEG; the quality is not applied.
4. A failed device-side upload NACKs with the protocol's generic `failed` code; no new error code was added.
5. ADR numbering: 0014 was the next free number after `origin/main`'s highest (0013), re-verified just before the PR.
