# P3.12 — Screensaver schedule

Side: build   Tier: standard   Depends on: P3.1
Verification: hardware
Issue: #70
Status: awaiting-hardware

## Why

F-SSV-18: an optional list of daily time slots, each with a start time and a mode; a slot lasts until the next starts and the last wraps past midnight. Slots may override brightness, the panel power-off delay, presence dismissal, widgets and At a Glance — but only turn off overlays configured globally, never invent them. Edits apply live, including to a running screensaver. The `schedule` trigger value for `tabula_screensaver` events already exists in TLP v1.

The engine is independent of the other mode packets and can run in parallel with them, but its hardware check can only exercise mode switching among the modes that exist when it runs; the script tests with clock and black first and the verifier adds other modes if their packets have landed.

## Do

1. The schedule engine (plain JVM): slot lookup for a wall-clock time, wrap-past-midnight, live re-resolution when settings change mid-run (including the running screensaver), and crossing into a slot. No day-of-week variation.
2. Entering a slot: switches the mode used next time; if the screensaver is running, it restarts in the slot's mode with trigger `schedule`; the event carries the mode actually shown (ADR 0013 item 3's stand-in rule still applies for unbuilt modes).
3. Slot overrides: brightness (fixed level or inherit global/adaptive — via the existing override path), widgets and At a Glance (turn-offs only, checked against global configuration), presence dismissal (P3.12 applies the flag; the presence source itself is out of scope and a configured-but-unbuilt feature is a no-op). The `power_off_delay` override is carried but no-ops until F-SSV-19 ships (noted in P3.1).
4. Crossing into a slot with a different power-off delay restarts that countdown — implemented as state now, effective when F-SSV-19 lands.
5. JVM tests: slot lookup across midnight, live edits, restart-on-cross, override resolution (cannot invent overlays), event trigger.
6. `tools/device/check_p312.sh` and a DEVICE.md section (slots set a few minutes ahead so the check runs quickly; `ha_events.py` captures the `schedule`-triggered events).
7. `PROVENANCE.md` rows.

## Out of scope

- F-SSV-19 (panel off after a while) and F-SSV-20 (wake behavior) as features.
- The HA presence source (F-SSV-24).
- Now-playing override (Phase 8).

## Result

Status: awaiting-hardware. CI part done; the hardware part runs
`tools/device/check_p312.sh` (docs/DEVICE.md, "Hardware check (P3.12)"),
which sets the slots itself — no manual configuration needed.

Built:

- **The engine (`ScheduleEngine`, core, plain JVM).** Maps a wall-clock
  time to the active slot and to the next slot's start: slots read by
  start time whatever order they arrive in, the last wraps past midnight
  into the next day's first start, a slot starts exactly at its start
  minute, and an off or empty schedule never answers. The engine knows
  only time: no settings, no rendering. No day-of-week variation
  (F-SSV-18 has none).
- **Controller resolution (F-SSV-18, ADR 0023).** The active slot is
  re-resolved on every tick and every settings push, crossings and edits
  by one rule: a running screensaver restarts when the mode it should
  show changed — both events trigger `schedule`, the started one carries
  the mode actually shown (the stand-in rule for unbuilt modes) — the
  same mode showing keeps the run, and turning the schedule off reverts
  to the global mode. The idle timer and HA commands still start and
  stop; the schedule only supplies the mode used next time, and a
  boundary landing on the idle deadline resolves first, so the idle
  start uses the new slot's mode. `nextEventMs` is the earlier of the
  idle deadline and the next slot's start, so crossings fire with no
  settings push, and the manager's loop waits on it.
- **Slot overrides resolve against each consumer's global configuration,
  and can only turn overlays off, never invent them.** The backlight
  holds the slot's fixed level while the slot runs (a live edit applies
  at once; `brightness_enabled` governs only the inherited global level,
  and black and dim keep their own levels even under a slot); the entity
  subscription drops widgets/At a Glance subscriptions for a slot's
  turn-offs and ignores a slot that tries to turn on what is off
  globally; the power-off countdown state restarts on a run restart or
  a delay change (consumed when F-SSV-19 ships) and the presence
  dismissal flag is carried (the F-SSV-24 source is a no-op until
  built) — both per the packet's Do items 3 and 4.
- **HA side: none needed.** The schedule's settings entities and options
  flow came with P3.1/P3.2 and are already tested there.
- **Docs and tooling:** ADR 0023, its README row, three PROVENANCE rows,
  the DEVICE.md hardware-check section, and
  `tools/device/check_p312.sh` (drives HA's options-flow API to set two
  slots a few minutes ahead on the tablet's own clock, captures the
  events with `ha_events.py`, checks the crossings, the live brightness
  edit and the panel levels mechanically, and turns the schedule off
  again at the end).

Deviations and design notes (recorded in ADR 0023):

- A same-mode crossing does not restart the run: F-SSV-18 asks for live
  application, and a stop/start would only flicker; the restart happens
  when the mode to show changes.
- ADR numbering: 0023 was the next free number — 0018 is held by open PR
  #98 and 0024 by open PR #122 (checked with `gh pr list` and
  `git ls-tree`); note ADR 0022 has no README index row on main (from
  P3.14's merge), left for the index-splitting PR #112 to carry.
- The engine reads slot starts in the tablet's current zone (local wall
  times, F-SSV-18); DST nights need no special case, and the schedule
  follows the tablet through timezone changes with no reconfiguration.
