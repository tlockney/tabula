# P7.0 — Voice device spike: mic persistence, wake word, echo cancellation

Side: build   Tier: deep   Depends on: none (Echo Show part: P2.7 bring-up)   Timebox: 3 working days
Verification: hardware
Issue: #25
Status: awaiting-hardware

## Why

ADR 0024 settles how voice joins HA: a native `assist_satellite` entity, audio over the existing connection, wake word on the device. Whether each v1 device type can be a voice satellite is still unknown. Fire OS withdraws mic permission from sideloaded apps at boot and after a Wi-Fi reconnect (FEATURES F-KSK-21); the Echo Show 8 has a mic array but its OS and audio stack in v1 are not settled. This spike measures each device type and ends in a go or no-go per type before any voice code is written.

## Questions to answer, with evidence

Run each on the Fire HD 10 Plus, and on the Echo Show 8 if it is in v1 at the time (on whichever OS it runs).

1. **Mic persistence.** Does `RECORD_AUDIO` granted with `pm grant` survive a reboot, a Wi-Fi drop and reconnect, and a day of uptime? If Fire OS revokes it, can the app or a provisioning step restore it without a person (an app-op, a device-admin or Shizuku route, a re-grant from the integration over the existing ADB host)? Record the exact step for DEVICE.md.
2. **Background capture.** Can a foreground service of type microphone capture while the dashboard, a screensaver or another app is in front, and with the panel off? What does the OS show the user while the mic is open?
3. **Audio input.** Which `AudioSource` values give usable 16 kHz mono PCM (`VOICE_RECOGNITION`, `VOICE_COMMUNICATION`, `MIC`)? On the Echo Show, does any source expose the mic array's beamformed or multi-channel input?
4. **Echo cancellation.** Is `AcousticEchoCanceler` available and effective while the device plays TTS or music? Test with a recorded clip: wake word spoken over the device's own playback.
5. **Wake word cost and accuracy.** Run microWakeWord (TFLite) continuously: CPU (`dumpsys cpuinfo`, `top`), heat, and detection rate on a short scripted set at 1 m and 3 m, with and without playback. Confirm the license of every model file you would ship; it must allow Apache-2.0 distribution. If CPU breaks the Phase 4 idle target (< 15%), measure the fallback instead: continuous upstream streaming of 16 kHz PCM, bytes per hour.
6. **HA round trip.** With throwaway integration code, feed captured audio to `async_accept_pipeline_from_satellite` over a binary handler on the device's existing WebSocket connection (ADR 0024 decision 2), and play the `tts-end` URL. Record latency from end of speech to start of reply.

**Answers, per question**

1. **Mic persistence — not measured, needs an owner-scheduled run.** The runs only show the grant being applied and read back (`granted=true`, and in one run `RECORD_AUDIO: allow; time=+1m42s403ms ago; duration=+10m0s58ms`). No run rebooted the tablet, cycled Wi-Fi or lasted a day, so survival across any of those is unknown. The restore step that needs no person is ADB (`pm grant`, or `appops set ... allow`); DEVICE.md carries it and ADR 0029 item 7 records it, with its necessity still unproven.
2. **Background capture — not measured, needs an owner-scheduled run.** The script's sections 4–4d were never reached, so there is no capture with the dashboard in front, another app in front, or the panel off, and no notification dump.
3. **Audio input — measured.** `MIC`, `VOICE_RECOGNITION`, `VOICE_COMMUNICATION` and `CAMCORDER` all open at 16 kHz mono 16-bit; `VOICE_CALL` is unavailable without a call session. Two quiet runs agree within about 4 dB. `UNPROCESSED` printed -38.1/-38.2/-38.3 dBFS across all three runs while every other source moved by roughly 30 dB between them, so its level does not track the room and it is not characterised here. ADR 0029 item 2 picks `MIC`, with `VOICE_RECOGNITION` as the fallback.
4. **Echo cancellation — measured, and absent as a platform effect.** `AcousticEchoCanceler.isAvailable()` is false, `NoiseSuppressor` and `AutomaticGainControl` report false, and none of the thirteen listed effects is a canceller. In the one run that clearly had playback going, the tablet's own voice sat 16.4 dB above the room floor and asking for the canceller on `VOICE_COMMUNICATION` removed 12.7 dB of it while the effect still reported `aec_enabled=false`, i.e. the audio HAL cancelled, not the Java effect. The second run reached only its silent and off passes (-60.1 then -58.4 dBFS, with a lower peak in the off pass than at rest), which looks like no audible playback and is not evidence either way. One usable 3 s window in one run is not a contract, so ADR 0029 item 3 makes detection half-duplex.
5. **Wake-word cost — CPU measured; heat, battery and accuracy not measured, needs an owner-scheduled run.** `cpu_pct` settles at 6.0 % of one core (7.7 % in the first 45 s) and `busy_pct` at 7.2 %, under the Phase 4 15 % target. The capture ran 445 s of a 600 s request and never printed its `done` line, so there is no `max_prob`, no detection count and no accuracy figure; the only temperature reading anywhere is 22.0 °C before the run, with no `during:` or `after:` sample. The streaming fallback measures 31,957 bytes/s, about 115 MB/h.
6. **HA round trip — not measured, needs an owner-scheduled run** once the binary channel from ADR 0024 decision 2 exists. It needs a throwaway integration on a test Home Assistant and a registered binary handler; neither is written, and a latency figure for that path would be a guess.

**Go or no-go**

No device type is cleared for voice by this packet. The Fire HD 10 Plus stays the Phase 7 target with the audio path settled (sources, echo cancellation, CPU), and its go is gated on one owner-scheduled run that closes questions 1, 2 and 5's accuracy. If the grant cannot be restored, background capture fails, or the clips do not fire, this device type gets no voice and stays a working kiosk without it (ADR 0024 item 1). The Echo Show 8 gets no verdict until P2.7's bring-up puts it on the network.
