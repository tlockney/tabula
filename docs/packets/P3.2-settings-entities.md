# P3.2 — Settings entities

Side: build   Tier: standard   Depends on: P3.1
Verification: ci
Issue: #60
Status: ready

## Why

FEATURES F-HA-11 turns settings keys into HA entities (switch / number / text) so automations and the HA UI can drive screensaver configuration without the Tabularium. Phase 2 shipped the state-backed entities only; ADR 0013 named the missing ones (master switch, idle timeout) as Phase 3 work. This packet adds the settings-backed entity set on the integration side, writing through the settings store so each edit reaches the device as a `set_settings` push.

## Do

1. Settings-backed entities per F-HA-11, each writing its key through the settings store as one revision (the P2.3 pattern: one write, one `set_settings` push):
   - switch: screensaver master enable (F-SSV-01), schedule enabled (F-SSV-18), widgets shown (F-WGT-01), screensaver brightness enabled (F-SSV-17).
   - number: idle timeout (a change starts the countdown over), screensaver brightness level (F-SSV-17).
   - text: clock background image source (each write reloads it even with the same value — F-SSV-09).
   - The screensaver mode select already exists from P1.3; extend its options only if the schema changed them.
2. The entity set per device is fixed by the schema version (not by capabilities), since settings exist for every paired device. Record this rule in an ADR (extends ADR 0009's territory; a new short ADR is fine).
3. Tests with the mock device: an entity edit produces one `set_settings` with a bumped revision; the mock's ACK stores the applied revision; concurrent edits do not interleave revisions; a device with a stale revision converges at registration.
4. `PROVENANCE.md` rows.

## Out of scope

- Button entities that trigger commands (postpone — not in Phase 3 scope; slide buttons — P3.9; screenshot button — P3.13).
- Panel-power entities and any F-SSV-19/F-SSV-20 behavior.
- The Tabularium (Phase 5).
