# P5.2 — Device list

Side: build   Tier: standard   Depends on: P5.1
Verification: ci
Issue: #150
Status: ready

## Why

The panel's first real page: every paired tablet with its identity, link state, versions and settings state, and a way into the per-device pages that P5.3–P5.8 fill. The hub already holds the records (`TabulaHub.devices`, `DeviceRecord`) and the HA device registry holds names, areas and the entity list; the panel should read one joined snapshot from the integration rather than stitching two registries together in the browser, so what the panel shows is what the integration believes.

## Do

1. **One snapshot command.** `tabula/panel_devices` (admin-only, from `panel_api.py`) returns a list, one entry per hub record: `device_id`, `ha_device_id`, name and model (record, falling back to the HA device registry), area id/name, `connected`, `last_seen`, `app_version`, `os_version`, `protocol_version`, `settings_schema_version`, `capabilities`, settings state (`ha_revision`, `device_revision`, `pending`), `current_page` and `screen` (from the reported state when present), and the device's entities grouped by platform so later pages (P5.5) need no second lookup. No credentials, tokens, pairing nonces or user ids.
2. **Last seen.** `DeviceRecord` gains `last_seen` (RFC 3339), written when a registered session ends and persisted with the device record, so an offline device shows when it was last connected across an HA restart. Keep it out of the device's state keys and out of settings.
3. **Panel list.** A devices route at `#/devices`: a table or card list with name, area, connection badge (online/offline with last seen), app version, and settings badge (in sync / update pending / device behind). Filter by name or area; sort by name with offline devices last; empty state pointing at the pairing flow. Selecting a device moves to `#/device/<ha_device_id>` and renders the device page shell with tabs (Overview, Settings, Logs, Activity) whose later tabs are filled by P5.3–P5.5; a direct link to that hash opens the right device.
4. **Freshness without polling.** The panel reloads the snapshot when it is shown (`visibilitychange`), after a failed call is retried by the user, and when HA fires a `tabula_*` event; it does not run a timer. A stale snapshot shows the time it was taken.
5. **Failures.** An unknown device hash shows a "device not found" state with a link back to the list; an offline device still opens its page (settings writes are stored, P5.3); a failed `panel_devices` call shows the error text and a retry button.
6. **Tests.** Python (`integration/tests/test_panel_devices.py`): admin-only; payload shape for an online and an offline device; `last_seen` recorded on disconnect and surviving a reload; a device with no HA registry entry still listed; no secret fields present. TypeScript (Vitest): list rendering for online/offline, filtering, sorting, empty state, unknown hash, error and retry.
7. **Manual check.** With the integration on a development HA and one mock device paired (then a second, disconnected one), the list shows both with the right badges and opens each device page. Paste what was observed.

## Out of scope

- Settings editing (P5.3), logs (P5.4), screenshots and command buttons (P5.5), profiles (P5.6), updates (P5.7), recovery controls (P5.8).
- Device health beyond link state and the state keys the device reports; the full health snapshot stays in HA's diagnostics download (F-MGT-06).
- Pairing, revoking or deleting a device from the panel. Device removal stays in HA's device page.
- A per-device event history; `DeviceRecord.events` is a diagnostic buffer, not a UI source.
