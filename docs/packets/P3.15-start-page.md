# P3.15 — Start page and return to it after idle

Side: build   Tier: standard   Depends on: none
Verification: hardware
Issue: #85
Status: awaiting-hardware

## Why

Today the app always opens HA's default page. F-DSH-02 asks for a per-device start target: the page opened on launch, after a crash or restart, and when the user or HA asks to go home. F-DSH-15 adds an optional return to that page after a period with no touch, so a tablet left on some other view resets itself, including overnight behind the screensaver. Both are small on top of what exists: the `navigate` command already resolves and checks frontend paths (PROTOCOL 4.5, ADR 0001 item 3), and the screensaver engine already tracks the last touch.

The page catalog (F-DSH-03) and a select listing every page are not built yet, so this packet sets the start target as a frontend path. A catalog-backed select replaces the text field when the catalog lands (Phase 4 navigation breakdown, #22).

## Do

1. Settings: add `dashboard.start_path` (a frontend path with a single leading `/`, optional fragment, no query; empty means HA's default page) and `dashboard.return_home_after` (seconds without touch; 0 means never). Both are `shared` role, with `x-tabula-feature` tags. Bounds and defaults go in an ADR 0002 extension; the default return is never, so existing tablets behave as today. Schema change rule: follow ADR 0015 item 7. If no build with the current settings schema version has shipped, add the keys to that version. Otherwise bump `schema_version` by one, which takes: a frozen copy of the previous schema (`settings.schema.v{n}.json`), a `DOWNS[n+1]` migration (the device codec is strict, `migrations/__init__.py`), `frozen_schema()` extended to the new frozen file, and `SettingsSchema.since()` (`settings.py`) walking every frozen version so older devices keep the settings entities they already have. Record which path was taken in the Result.
2. Device, start target: load `start_path` on launch, on the reload after a crash or restart, and on "go home". Validate it the same way `navigate` does; an invalid or off-origin value falls back to HA's default page and logs a warning. Changing the setting does not move the page on screen (F-DSH-02). A fragment is kept (F-DSH-02).
3. Device, return after idle (F-DSH-15): after `return_home_after` seconds with no touch, navigate to the start target if the WebView is not already on it. The timer keeps running behind a screensaver, so the page resets without lighting the screen. It is reset by any touch and by HA navigation (the HA-navigation reset is independent design; mark it so in PROVENANCE). View freeze, page-declared interactions and the swipe map do not exist yet; leave a single hook where they would pause the timer, with a comment naming F-DSH-17 and F-DSH-18.
4. Go home: add a `go_home` command (capability `go_home`, additive per PROTOCOL 8, with fixtures and validator coverage) and a "Go to start page" button entity (F-HA-08 candidate, confirmed here). Restart lands on the start target (F-NAV-03); reload keeps the current page.
5. Integration: the two keys appear in the options flow and as settings entities per ADR 0015 (a text entity for the path, a number for the delay). Record in a short ADR that the start target is a text setting until the page catalog exists, answering the F-DSH-02 and F-HA-10 open questions for now.
6. Mock device: `go_home`, start path on (re)registration, and the idle return driven by a fake clock, so the conformance suite covers it.
7. Tests: JVM tests for path validation and the idle-return timer (fake clock: touch resets, runs behind the screensaver, no navigation when already home); integration tests for the migration, entities and button → command.
8. `tools/device/check_p315.sh` and a DEVICE.md section; `PROVENANCE.md` rows.

### Schema change path taken

No build with settings schema v2 has shipped (no git tags, no releases), so both keys were **added to v2** — no version bump, no new frozen schema, no new `DOWNS` entry. `DOWNS[2]` prunes against the frozen v1 schema, so `dashboard` is dropped for v1 devices automatically (proven by the extended v2 `full.json` fixture in `test_v2_document_translates_down_to_strict_v1`), and `SettingsSchema.since()` needed no change (the frozen v1 walk yields 2 for the new keys).

### What was built

1. Settings: `dashboard.start_path` (0–2048 chars, empty or single-leading-slash path, optional fragment, no query; default "" = HA's default page) and `dashboard.return_home_after` (0–86400 s, default 0 = never), both `shared` role, `x-tabula-feature` F-DSH-02 / F-DSH-15. Kotlin regenerated (`make codegen`); ADR 0002 gained the bounds rows.
2. Device: `StartPageController` (android/core, plain JVM, fake-clock tests) counts the return from the last touch or page change, keeps running behind a screensaver and while the panel is off, has a single `setHeld` hook reserved for F-DSH-17/F-DSH-18, skips navigation when the page is already the target (path-only compare, so a fragment target counts as home), and restarts the countdown when the delay changes. `StartPageManager` (app) runs it against the clock and loads via `DashboardBus.loadStart()`. `DashboardView` loads the validated start path on launch — fragment kept, the external-auth parameter appended before the fragment (`DashboardLinks.withParam`) — and falls back to HA's default page with a warning log when the value is empty, invalid or off-origin (same validation as `navigate`, `resolveNavigatePath`). Changing the setting never moves the page. `restart_app` relaunches through the launch path, so it lands on the target; `reload` untouched.
3. `go_home` command: TLP `command_go_home` frame (empty args) + golden fixture, `x-tabula-frames` entry, PROTOCOL 4.5 row, and the `go_home` member of the `$defs.capability` enum (additive per PROTOCOL 8; the integration's and mock's schemas updated identically). The app declares the `go_home` capability; `TabulaCommands.GO_HOME` fails with `failed` when no dashboard is showing (PROTOCOL 6), like reload/navigate.
4. Integration: a "Go to start page" button (capability `go_home`, F-HA-08 candidate confirmed), a `start_path` text entity and a `return_home_after` number (both schema-version-gated settings entities per ADR 0015; the text and number classes were generalized to `TabulaTextSetting` / `TabulaSettingsNumber`); the options flow picks both up from the schema automatically. `strings.json` + `translations/en.json` updated.
5. Mock device: `go_home` (start path validated with `same_origin`, `invalid_args` when off-origin; unset target navigates to `/`), the start path applied on (re)registration, and `touch()`/`tick()` driving the idle return from an injectable clock; a changed return delay restarts the countdown (parity with ADR 0021 item 5). ### Deviations and design decisions

- All open questions are recorded in **ADR 0021** (start target as a text settings path until the page catalog, answering F-DSH-02/F-HA-10 for now): the countdown is reset by any touch and by any page change (the HA-navigation reset is the independent design — a page change is the observable form of HA navigating), it is not paused by the panel or the foreground, and a changed delay restarts it while a changed path does not navigate.
- `go_home` also joined the `$defs.capability` enum in `schema/tlp-v1.schema.json`; the packet's "fixtures and validator coverage" is the `command_go_home` fixture plus the TLP codec (`Tlp.kt`) and `TlpFixturesTest` entries.
- The schema text-entity change reused the existing `TabulaClockBackground` class as a generic `TabulaTextSetting` (same behavior, one more description); no entity behavior changed for the clock background.
