# P3.9 — Gallery HA media browser source and slide controls

Side: build   Tier: standard   Depends on: P3.8
Verification: hardware
Issue: #67
Status: ready

## Why

The remaining F-SSV-12 sources: a single image, a folder of images or video files from HA's media browser — the device browses HA over its credential, builds the playlist when the screensaver starts, and plays videos muted (whole or cut to the photo interval). This packet also adds the only TLP change in Phase 3: the `slide` command behind HA's next/previous-slide buttons (F-SSV-12's HA entities).

Protocol note: `slide` is a new command frame type gated by a new capability (`photos`), which is additive under PROTOCOL 8 — no protocol-major bump. Fixtures, the Python and Kotlin codecs, the mock device and the integration's schema copy all gain it in this packet.

## Do

1. TLP addition first: `slide` (`command_slide`), args `direction: next | previous`, capability `photos`. Schema entries in `schema/tlp-v1.schema.json` and the integration's copy, valid + invalid fixtures, Kotlin codec types, mock device handling, `make frames` green. Update PROTOCOL 4.5's table (no major bump; note the addition under section 8's rules). Add `slide → {photos}` to `const.py`'s command→capability map. The result says whether the slide actually moved (F-MGT-08 — the last/first-slide case inside a photo mode): the packet's ADR picks the mechanism, and a `moved` field in the result's `data` is the additive option (PROTOCOL 8; the `command_result.data` fixture already exists), with explicit deferral of the F-MGT-08 wording as the alternative. If the result carries data, update PROTOCOL 4.6's statement that no other command returns data in v1 in the same pull request. Also add a conformance/integration test in which a `photos`-declaring device registers against an integration that does not know the capability: the capability is dropped, not rejected (PROTOCOL 4.0), and the integration never sends `slide` to it.
2. Device: browse HA's media browser over the WebSocket with the device credential (an ADR records which commands, the content-url authentication rules, and the size/refetch limits — the P2.5 credential rules apply: the fetch attaches no credential the browser's signed URLs do not require, and never to non-HA hosts).
3. Playlist from the chosen source (single image, folder, or video files) built at screensaver start; images via the P3.8 pipeline; videos play muted, either whole or cut to the photo interval, reusing the P2.5 media player machinery where it fits.
4. Slide stepping: edge taps already step (P3.8); the new `slide` command does the same (a no-op outside photo modes → `ok`, not `failed`, per F-SSV-12's "no-op in other modes" — record this in the ADR or PROTOCOL wording).
5. Integration: next-slide and previous-slide button entities, created when the device declares the `photos` capability; the service path sends `slide` and awaits the result.
6. Tests: codec/fixture tests for `slide`; integration tests for the buttons (capability-gated creation, ACK, no-capability device gets no buttons); JVM tests for the browser client and playlist build against a fake HA (the mock server's pattern); the mock device handles `slide` in conformance.
7. `tools/device/check_p39.sh` and a DEVICE.md section.
8. `PROVENANCE.md` rows.
