# P3.7 — Weather screensaver

Side: build   Tier: deep   Depends on: P3.5
Verification: hardware
Issue: #65
Status: ready

## Why

F-SSV-11: an animated sky reflecting the condition of a chosen HA weather entity and the time of day from HA's sun entity (local-time fallback), with optional clock and info-bar overlays. Rendering must stay smooth on weak hardware and pause when the panel is off or the app is backgrounded. The plan fixes the strategy: Canvas animation on API < 33, AGSL optional on 33+ — the v1 devices are API 28 (Fire OS 7), so the Canvas path is the one the hardware check exercises; the AGSL path cannot be verified on any current target and is CI-verified only until an API 33+ device exists.

Unverified device fact this packet depends on: CPU headroom on the HD 10 Plus for continuous animation (the Phase 2 hardware checks #15–#20 have not run, and nothing has measured the SoC under load yet). The packet starts with a timeboxed device spike that measures fps and CPU during the animation, recorded in an ADR; the animation's elaborateness for v1 is chosen from the measurement, per the "Open" line in F-SSV-11.

## Do

1. **Timeboxed device spike (first, timebox: 1 working day)**: a minimal Canvas animation on the Office Kiosk over the screensaver brightness; measure frame rate and CPU (`dumpsys gfxinfo` / `dumpsys cpu`) for a bounded period; paste into an ADR and pick the v1 animation budget from it. If smoothness cannot be held, degrade (fewer layers, longer frame interval) rather than hand back — the ADR records the budget chosen.
2. Condition model (plain JVM): every standard HA weather condition × time of day (dawn/day/dusk/night from the sun entity, local-time fallback), mapping to a scene description the renderer consumes; unknown condition → plain overcast scene; no reading yet → overcast; dropouts keep the last condition (F-SSV-11).
3. Canvas renderer for API < 33: a custom view drawing at a bounded frame rate; pauses when the panel is off or the app is backgrounded (reuse the P2.4 pause signals); resumes without replaying.
4. AGSL path, optional on API 33+: compile-time-guarded (compileSdk 34), selected at runtime by API level; the same scene description drives both renderers. If the AGSL path doubles the maintenance cost for no measurable gain on weak hardware, the ADR may decide to ship Canvas-only — say so explicitly either way.
5. Overlays: optional clock and info bar (temperature, condition, daily high/low when the entity has a daily forecast, humidity, wind, visibility, apparent temperature, optional place name), using P3.5's forecast access; blur behind overlays optional; lightning toggle. No entity chosen → a prompt to pick one.
6. Local preview: an ADB-reachable way (a broadcast or settings key) to force any condition/time of day without HA, for the hardware check and tuning.
7. JVM tests: the condition model (mappings, fallbacks, sun/local-time), info-bar formatting (F-AAG-03 rules), pause/resume, scene-description invariants.
8. `tools/device/check_p37.sh` and a DEVICE.md section, including the spike measurements.
9. `PROVENANCE.md` rows.

## Out of scope

- Weather corner widgets and forecasts outside the info bar (P3.11).
- Radar or map imagery.
- Calendar mode and other screensaver modes.

## Done when

- CI: `make check` passes with the new JVM tests; the AGSL path compiles in CI.
- Hardware (pasted by the hardware verifier): the spike ADR's measurements; with a weather entity configured, the tablet shows the sky for its current condition and follows a condition change and a sun-entity time change; the preview control forces other conditions; fps/CPU within the ADR's budget on the Canvas path. `check_p37.sh` output pasted.
- `PROVENANCE.md` updated.
