# P10.3 — On-device camera presence detector

Side: build   Tier: deep   Depends on: P10.0, P10.1 (go), P10.2
Verification: hardware
Issue: #90
Status: ready

## Why

The tablet's front camera becomes a presence source (plan 7.6). P10.0 specifies the behavior, P10.1 decides whether and how the Office Kiosk can run it, and P10.2 provides the presence rule it plugs into. This packet builds the camera source on the device and the protocol it needs. The HA entities follow in P10.4.

## Read first

- `AGENTS.md`
- `docs/FEATURES.md`: the camera-presence entries from P10.0, F-SSV-24, F-DSH-09 (genuine tap for camera features)
- `docs/PLAN.md` section 7.6 (device constraints)
- The P10.1 ADR (camera API, detector, frame budget, privacy commitments, provisioning) and the P10.2 ADR (`PresenceSource`, `PresenceRule`)
- `docs/PROTOCOL.md` sections 4.4, 4.7 and 8; `schema/tlp-v1.schema.json`, `schema/fixtures/`

- `android/core/`, `android/app/` (manifest, `TabulaService`)

## Do

1. `CameraPresenceSource` implementing P10.2's `PresenceSource` with the detector, resolution and frame rate the P10.1 ADR chose. Frame analysis in plain JVM code where it can be (`android/core`, unit-tested with synthetic frames); camera plumbing in `android/app`.
2. Privacy, as committed in the P10.1 ADR and the P10.0 entries: frames stay in memory, are never written to storage or logs and never leave the device; only presence state does. Off by default. Runs only when the spec says it may (for example while a screensaver shows or the panel is off). The user-visible indication the spec requires.
3. Permission: missing camera permission → the source reports unavailable, logs once and does not prompt; enabling it needs the on-device tap or the ADB grant from DEVICE.md.
4. Cost control: the frame budget from the ADR as ADR 0002 constants; the camera stops whenever no rule needs it (dashboard in use, another app in front, feature off).
5. Protocol: state keys for camera presence and for "camera active", gated by a new `camera_presence` capability (additive per PROTOCOL 8), declared only with a front camera and the permission. Any events the spec requires go through PROTOCOL 4.7. Fixtures and validator coverage.
6. Settings: the keys the spec names (enable, detector kind, sensitivity and similar), with an ADR 0002 extension. Schema change rule: follow ADR 0015 item 7. If no build with the current settings schema version has shipped, add the keys to that version. Otherwise bump `schema_version` by one, which takes: a frozen copy of the previous schema (`settings.schema.v{n}.json`), a `DOWNS[n+1]` migration (the device codec is strict, `migrations/__init__.py`), `frozen_schema()` extended to the new frozen file, and `SettingsSchema.since()` (`settings.py`) walking every frozen version so older devices keep the settings entities they already have. Record which path was taken in the Result.
7. Mock device: the capability, state keys and a scripted presence sequence.
8. Tests: JVM tests on synthetic frames (motion vs noise, dark frames), lifecycle tests (camera stops when not needed), protocol fixture tests.
9. `tools/device/check_p103.sh` (includes the CPU and battery measurement from P10.1's script, now against the production path) and a DEVICE.md section; `PROVENANCE.md` rows.

## Out of scope

- HA entities and the options flow for these settings (P10.4).
- Camera views, streams, snapshots, hand gestures.

## Done when

- CI: `make check` passes with the new tests and fixtures.

- `PROVENANCE.md` updated.
