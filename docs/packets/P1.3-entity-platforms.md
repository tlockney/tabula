### Behavior

- State deltas go from `tabula/state` through `TabulaHub.apply_state` to a per-device dispatcher signal carrying the changed keys. Each entity writes its state at most once per frame, and only when one of its keys changed. The device already coalesces to one frame per `STATE_MIN_INTERVAL`.
- Availability: an entity is available while the device has a current registered connection and still declares the entity's capability. The connectivity sensor is the exception: it stays available and reads off when the link drops (FEATURES F-HA-09 left this open; settled here).
- Nothing is removed on disconnect. Capabilities are stored with the device record, so after an HA restart the entities exist, unavailable, before the tablet reconnects. A capability dropped at registration removes its entities from the entity registry (FEATURES F-HA-02); a capability gained adds them.
- Superseded connections: the old socket closing does not mark the device unavailable, because only the current session's cleanup clears `record.current`.
- Control actions (light on/off, switch, number, select, buttons, media player, notify) are wired to the TLP commands they will send, but raise `HomeAssistantError` (`commands_unavailable`) until P1.4 adds command dispatch.
- Entities look up their device record through the hub on every read, so re-pairing a tablet (a new record for the same device id) or deleting and re-pairing it keeps or recreates its entities. Every registration syncs the entity set, so a tablet with no capabilities still gets its always-present entities.
- P1.2 review follow-up: each new pending pairing gets an expiry timer (`PAIR_PENDING_TTL`, no new constant), so a confirmed but unclaimed credential is revoked even when no further pairing traffic touches the pending store. If the entry expires while the confirm step is still creating the credential, the flow revokes it and aborts with "expired". Revocation only touches the record whose token that attempt created.

### Deviations

- **Dashboard view select (plan 5.5 select row, FEATURES F-HA-10) is not in P1.3.** Its options come from HA's dashboards and panels and choosing one sends `navigate`, so it belongs with P1.4 (commands) or later; it needs a design for building and caching the option list.
- Switches for keep screen on and adaptive brightness, and the screensaver number and select, will write settings (plan 5.6) rather than send a dedicated command. Their action methods name `set_settings` as a placeholder; P1.4/P1.5 decide the exact path.
- Test fixture: the `integration` fixture now also sets up the `media_player` and `notify` components before the test HTTP server starts, because they register HTTP views and aiohttp freezes the router once it runs (HA's own startup order does this).
