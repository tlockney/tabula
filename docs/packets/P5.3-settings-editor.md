# P5.3 — Schema-driven settings editor

Side: build   Tier: deep   Depends on: P5.1, P5.2 (the settings store from P1.5 and schema v3 from P3.1 are merged)
Verification: ci
Issue: #151
Status: in-review

## Why

Plan 5.6 and F-MGT-01 make HA the only place settings are edited, and the panel the place that edits them; until now the options flow is the only editor. This packet adds the per-device editor, generated from the schema so that schema v4 (P5.7) and every later key need no new UI code. The hard parts are not the widgets: it is per-key validation and rejection (valid keys must still apply), one revision and one push per save, a device schema version that can be older than HA's, and the two structured lists the schema already has (At a Glance entities and schedule slots).

## Do

1. **Read command.** `tabula/panel_settings` (admin-only) takes `device_id` and returns the HA revision, the device's reported revision, whether a push is pending, the device's settings schema version, the stored document (or the schema defaults when the device has none, with a `stored` flag), the schema defaults, and the device's capability list. Settings never travel the other way: no device credential, token or pairing detail is in the payload.
2. **Write command with per-key results.** `tabula/panel_settings_set` takes `device_id` and `values` (`{flat_key: value}`, the generated `SettingsField.key`). It validates each submitted leaf against that leaf's schema (type, bounds, pattern, enum, array items, required slot properties) and then saves the valid keys as **one** revision through `async_set_settings`, so the device never sees half a change (ADR 0011). The response is `{revision, applied: [...], rejected: [{key, reason}]}`; F-MGT-01's rule is that rejected keys come back with reasons and the valid keys still apply. Nothing valid means no save and no revision bump. Unknown keys, non-leaf paths and a value of the wrong shape are rejected per key, not as a 500.
3. **Revision and push.** The save bumps the revision and schedules the push exactly as entity and options-flow writes do; an offline device keeps the stored write and receives it at its next registration (plan 5.6). A successful response carries the new revision so the editor can show "applied on the device" only after the ACK, not after the save.
4. **Older devices.** Keys introduced after the device's `schema_version` (the metadata's `since` needs; P3.2's `SettingsSchema.since` has the mapping) stay visible and editable but carry a "the device receives this after it updates" note; the store already holds and prunes by migration (plan 5.4). Nothing is silently hidden or dropped.
5. **Editor UI.** The device page's Settings tab renders sections from `SETTINGS_FIELDS` in schema order, with humanized labels and the schema description as help text, in a panel string table (no per-key labels in component code):
   - booleans as switches; integers as a number input plus slider at the schema bounds; strings with `maxLength` and `pattern`; enums as selects; colors (`#RRGGBB`/`#AARRGGBB` pattern) with a text input and a colour swatch;
   - nested groups (`screensaver.clock`, `screensaver.night_mode`, `screensaver.weather`, `screensaver.photos`, `screensaver.website`, `screensaver.pixel_shift`, `screensaver.fade`, `widgets.*`) as collapsible sections;
   - `at_a_glance.entities`: add/remove/reorder rows with an entity picker fed by `hass.states` and the schema's entity-id pattern;
   - `schedule.slots`: repeatable rows (start time, mode, nullable brightness/power-off/overrides with an explicit "inherit" state), add/remove/reorder, kept in start-time order as the schema requires; `additionalProperties: false` and required `start` are enforced before submit.
   Client validation mirrors the metadata for immediacy only; the server response is what the form reports.
6. **Save behaviour.** Dirty tracking per section, a save action for the whole form (one revision), a leave-page guard while dirty, field-level display of rejected keys with the server's reason, and a top-level summary for keys that applied. A device that goes offline mid-edit keeps the user's draft and says the write will be delivered on reconnect.
7. **Tests.** Python (`integration/tests/test_panel_settings.py`): admin-only and unknown device; read for a stored device and for a device with no document; one revision and one push for a multi-key write; per-key rejection with valid keys applied; no revision when every key is rejected; unknown/non-leaf keys; offline write stored and pushed after reconnect (the existing e2e pattern); a key above the device's schema version stored but not pushed by a v1 translate-down; no secrets in either payload. TypeScript: one Vitest case per control type, nested groups, both array editors (including inherit), dirty guard, rejection display, pending/applied revision.
8. **Manual check.** With `mockdevice` paired and online, change the idle timeout and a clock colour, see the revision go applied; submit one invalid and one valid value together and see the invalid one rejected while the valid one applies. Paste what was observed.

## Out of scope

- Profiles, overrides and drift (P5.6). The editor edits the device's own document only.
- The recovery PIN and recovery toggles (P5.8); secrets and write-only fields generally, since schema v3 has none.
- A settings diff against the previous revision, undo, or import/export (F-MGT-05, later).
- Changes to the schema itself: any new key is a separate schema bump with its own packet.
- Reworking the options flow; it stays the editor for Phases 1–4 and shares only the schema metadata.

### Per-key validation: leaf subschema first, assembled document as the guard

Each submitted leaf is validated against **its own property subschema** from
`schema/settings.schema.json` (`Draft202012Validator` over that node; the schema
uses no `$ref`, so a property node is self-contained). That is the design the
packet's rule needs: a whole-document check fails every key together, while a
per-leaf check gives F-MGT-01's "rejected keys come back with reasons and the
valid ones still apply" for free, including inside the two array leaves — a slot
without `start`, an `additionalProperties` violation or a bad entity id is that
leaf's rejection, not a 500. The accepted keys are then applied to a copy of the
stored document and the **assembled document is validated once**, so a rule that
spans keys (none today) still refuses rather than half-saving; a problem's path
names the submitted keys it runs through, and those are moved to `rejected` with
the schema's message. If the document check finds nothing to blame, every
accepted key is rejected with those problems — nothing is saved on a document
that fails the schema. Unknown keys and group paths are rejected before any
validation, with distinct reasons ("No setting has that name." / "This is a
group; set the keys inside it instead.").

### Deviations

- **The manual check was not run.** This packet is `Verification: ci` and this
  machine runs no Home Assistant instance and no browser session against one, so
  there is no observation to paste and no HA version to name — the same deviation
  P5.1 and P5.2 recorded. The pytest suite drives the real WebSocket surface and
  the real mock device (one push per save, offline write delivered on reconnect,
  a v3 key stored but not pushed to a schema-1 device), and the Vitest suite
  drives every control, both array editors, the dirty mark, the leave guard, the
  rejection display and the applied/awaiting states in a DOM. What no test here
  shows is the bundle rendered inside a live frontend; that needs a follow-up
  task on a machine with a running HA.
- **`field_since` is in the read payload.** The packet asks for the device's
  schema version and for newer keys to carry a note; the panel needs to know
  each key's introducing version, which lives in Python's schema walk
  (`SettingsSchema.since`), not in the generated TypeScript. Sending the map
  keeps one implementation of the rule instead of adding a second schema walk to
  the codegen.
- **Array item metadata comes from the codegen, not hand-kept.** The generic
  schedule editor needed each slot property's bounds, enum and nullability. The
  alternative — a hand-kept slot shape in panel code — would have been the one
  hand-maintained field list the project forbids, so `tools/codegen_ts.py` now
  emits it and `make codegen-drift` keeps it honest. Kotlin generation is
  untouched.
- **Object arrays are shown in stored order and sorted on save.** The schema
  requires start-time order; sorting the displayed rows would make the up/down
  buttons look inert for slots that already have a start, so the form keeps the
  rows where the user put them and `saveValues` sorts them into the schema's
  order when the list is submitted.
- **`identity.name` still applies through the options flow's rule.**
  `hub.apply_identity` is called after a save, so a name typed in the panel
  renames the HA device exactly as it does from the options flow.
- **A failed load retries once per device, not per render.** The element records
  the device it attempted, so a failed read shows the error and a retry button
  instead of looping through Lit's update cycle.
- **No new constant and no new ADR.** Bounds, patterns and defaults all come
  from the schema; the next free ADR number (0035) is untouched.

### Open questions for the architect

- The editor shows the identity and connection groups too, because the schema's
  role tags make them editable (`EDITABLE_ROLES`). The options flow has always
  done the same, so this matches; if the panel should keep `connection.ha_url`
  out of an admin's hands once the recovery page (P5.8) exists, that is a role
  decision, not a panel one.
- A save re-reads `tabula/panel_settings` to learn the ACK. If the fleet grows
  to many simultaneous editors, a `tabula_settings_applied` event would remove
  the second round trip; today one read is cheap and keeps the rule in one
  place.
