# P10.4 — Camera presence in HA (entities and settings)

Side: build   Tier: standard   Depends on: P10.3
Verification: ci
Issue: #91
Status: ready

## Why

With the camera source on the device (P10.3), HA needs to show it: a presence binary sensor that automations can use (a tablet in every room is also a room sensor), a "camera active" indicator so the household can see when the camera runs, and the settings to control it. This packet is integration-side only and is driven by the mock device, so it needs no tablet.

## Read first

- `AGENTS.md`
- `docs/FEATURES.md`: the camera-presence entries from P10.0, F-HA-02, F-HA-04
- `docs/PLAN.md` sections 5.5 and 7.6
- The P10.3 ADR and its PROTOCOL changes; `docs/decisions/0009-entity-model-p1.md`, `0015-settings-entities.md`
- `integration/custom_components/tabula/` (`binary_sensor.py`, `const.py` capability map, `options_flow.py`, `settings.py`)
- `mockdevice/`

## Do

1. A presence `binary_sensor` (device class `occupancy` or `motion`, chosen in a short ADR note with the reason) and a "camera active" `binary_sensor`, both created only with the `camera_presence` capability; unavailable on disconnect (F-HA-04).
2. Options-flow fields and settings entities for P10.3's keys, per ADR 0015. ADR 0015 item 2 gates settings entities by schema version only, which would show camera settings on tablets without a front camera (against F-HA-02). Amend ADR 0015 so capability-bound settings entities also require their capability (here `camera_presence`), with tests for a device with and without it.
3. Any events the spec requires, fired as `tabula_*` events.
4. Integration tests against the mock device: capability on/off, state round trip, settings round trip.
5. `PROVENANCE.md` rows.

## Out of scope

- Device code (P10.3).
- Camera views or snapshots in HA.

## Done when

- `make check` passes with the new tests.
- `PROVENANCE.md` updated.
