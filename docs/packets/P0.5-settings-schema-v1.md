Side: build   Tier: standard   Depends on: P0.2r, P0.4
Verification: ci
Issue: #8
Status: done

## Why

Settings are data defined once in JSON Schema. Python loads it, and Kotlin (P2.0) and TypeScript (Phase 5) are generated from it.

## Read first

- `AGENTS.md`
- `docs/PLAN.md` sections 5.6 and 7.1 (P0.5)
- `docs/FEATURES.md`
- `docs/PROTOCOL.md`
- `docs/decisions/0002-constants.md`

## Do

1. Write `schema/settings.schema.json` covering only what Phases 1–2 use: identity, connection, screen, screensaver, notifications and audio.
2. Set `schema_version: 1` and put a role tag (`identity`, `connection`, `hardware`, `shared`) on every property.
3. Take every default from ADR 0002.
4. Add a defaults fixture and a set of known-bad fixtures, with pytest tests.

## Out of scope

- Kiosk, gestures and update settings (added by the phases that build them).
- Code generation (P2.0).

## Done when

- `make test` passes, including tests that the schema accepts the defaults fixture and rejects each known-bad fixture.
- `make check` passes.

## Hand back

Result section: property list by role, test output.

### Deviations / decisions

1. Role assignment (FEATURES does not define the tags): `identity` and `connection` keys are never shared by profiles (F-MGT-03) and connection keys are the only ones recovery may change (F-MGT-11). Brightness and volume levels are tagged `shared` because F-MGT-04 says a profile may carry them (new profiles just start without them). No v1 property is `hardware`: the F-MGT-03 hardware choices (audio output, UI scale) arrive with the phases that build them; the role is in the tag set now so profile enforcement is stable.
2. `audio.announce_volume_boost` is an enum with the single value `none` (default per ADR 0002). FEATURES names no boost feature; the single value pins "announcements play at the current volume" and leaves room for a later ADR to add boost levels.
3. Assistant, notification and alarm volume channels (F-TTS-07) and the notification sound library (F-NTF-10) have no ADR 0002 defaults, so they are not settings in v1. P2.5 adds the notification volume (F-NTF-09) together with its ADR 0002 default; the other channels wait for their own ADR rows.
4. Bounds: `screensaver.idle_timeout` 1–86400 s and `notifications.max_visible` 1–10 are recorded in ADR 0002 ("Settings bounds in the settings schema"), so P2.0's generated Kotlin can use `Int` everywhere. The rest reuse ADR 0002's existing bounds: brightness 0–100 and the `screensaver.mode` / notification-level enums match `schema/tlp-v1.schema.json`'s state keys; `identity.name` maxLength 64 is ADR 0002's identifier bound; `default_duration` 0–3600 (0 = until dismissed) is ADR 0002's `notify.duration` bound. `ha_url` accepts only scheme, host, optional port and optional path — no userinfo, query or fragment — the rule `play_media.url` already applies to userinfo; credentials in the URL would be stored and exported with settings, and a query or fragment breaks relative-path resolution (PROTOCOL 4.5).
5. `identity.name` and `connection.ha_url` have no defaults: a device keeps the name/address it already has. Missing keys everywhere mean "keep the device default" (PROTOCOL 4.5).
6. `chime_by_level` is an object keyed by severity so ADR 0002's per-level default (chime for `warning` and `error`, silent otherwise) is expressible directly.

### Review round (PR #40)

- Added `maximum` 86400 to `screensaver.idle_timeout` and 10 to `notifications.max_visible`, with both minima and maxima recorded in ADR 0002; added invalid fixtures `idle_timeout_over_max` and `max_visible_over_max`.
- Restricted `connection.ha_url` to scheme, host, optional port and optional path (`^https?://[^/@\s?#]+(/[^\s?#]*)?$`); added invalid fixtures `ha_url_userinfo` and `ha_url_query`.
- Nits taken: the ADR's notification-duration row now says 0 means until dismissed; the schema description states no v1 property carries the `hardware` role, so codegen must not assume every role has members.
