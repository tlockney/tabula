# P9.2 — Intercom in the integration: signaling relay, services, events, sensor

Side: build   Tier: deep   Depends on: P9.1
Verification: ci
Issue: #140
Status: in-review

## Why

HA is the directory and signaling path for intercom (ADR 0025 decisions 4 and 5). This packet adds the HA side: the services that start and end calls from buttons and automations, the relay that carries offers, answers and candidates between two devices, the events automations follow, and a state sensor per device.

## Do

1. Services `tabula.intercom_call` and `tabula.intercom_end` (ADR 0025 decision 5). `intercom_call`: standard target (devices, or areas resolving to Tabula devices), `mode` (`call` or `broadcast`), caller device in service data. No target in `broadcast` mode means every `intercom_listen` device except the caller. Targets without the capability are skipped; if none remain, raise a validation error (nothing fails silently). `intercom_end`: ends a call by call id or by device and reaches every device in the call in every call state, including one that is ringing, connecting or in progress.
2. Call state in the integration: one record per call (id, caller, callees, mode, state, started time). Relay `intercom_signal` between the two peers of a call. Only devices of the same Tabula hub can call each other. Refuse a two-way call when caller and callee share an area (ADR 0025 consequences) with a clear error; broadcast to a same-area device is skipped, not an error.
3. Timers owned by the integration: ring limit (`INTERCOM_RING_LIMIT_S`) ends an unanswered call as missed; connect timeout (`INTERCOM_CONNECT_TIMEOUT_S`); hard call limit (`INTERCOM_CALL_LIMIT_S`) sends `intercom_end` to every device in the call.
4. Disconnect handling (guard 4): when a device in a call disconnects or re-registers, the integration ends the call for the other side and never re-rings or resumes. A device's registered `intercom_state` that is not idle after a restart is answered with `intercom_end`.
5. Events on the HA bus: `tabula_intercom_started`, `tabula_intercom_answered`, `tabula_intercom_missed`, `tabula_intercom_ended` with call id, caller, callees, mode and reason. Add them to the events list that `events.py` already forwards.
6. A sensor per intercom-capable device for `intercom_state` (idle, ringing, in_call, broadcasting), created only from the capability.
7. Handle `intercom_start_request` events from a device (its own screen starts a call): resolve the target the same way as the service and run the same code path.
8. `services.yaml` and `strings.json` text for the services; translation entries.
9. Tests with the mock device: call, answer, decline, missed (ring limit), connect timeout, hard limit, end from HA in each state, device disconnect mid-call, no resume after re-register, area refusal, broadcast target set, capability gating (a device without the capability is never sent a ring), two simultaneous calls on different pairs, a device already in a call refusing a second.
10. `docs/provenance/P9.2.md`: independent design.

## Out of scope

Any Android code (P9.3), voice intents (P9.6), auto-answer settings (P9.5), WebRTC itself (the relay passes opaque payloads).

The four production guards from ADR 0028 are requirements, not options: (1) a call starts or is answered only through an explicit action or a schedule, never because a device is online; (2) a hard call time limit; (3) `tabula.intercom_end` reaches every device in the call in every call state; (4) no call resumes after a device restarts.

Audio rule (owner, binding): no test, script or run in this packet plays or captures audio on a household device unless the owner schedules it. Silent analysis, unit tests and CI are fine. Do not run `tools/device/check_p90*.sh`, `check_p70.sh` or set `TABULA_AUDIO_OK`.

The tests drive each tablet as a raw WebSocket client built from the golden TLP fixtures: commands are recorded and answered on the wire, so what the assertions see is what a tablet would receive. HA's call-later timers are advanced with the harness's thread-safe `fire_time_changed` rather than slept through. The timer job is a `@callback` function, not a lambda: HA inspects the job's target and runs anything that is not a callback in an executor thread, where `hass.async_create_task` is not allowed, so a lambda wrapper would have moved the end work off the loop in production too. Every callback in the module schedules with `hass.async_create_task` and the integration calls no loop methods of its own.

### Decisions taken here (in the packet's gift)

1. **A call id is used once.** A device chooses the id of a call it starts, so a request naming an id already in `calls` is refused and logged rather than overwriting the live call's record, which would strand its tablets with no `intercom_end` and no ended event. The service path mints a ULID, so it cannot collide.
2. **The caller is an HA device registry id**, with a device selector in `services.yaml` filtered to the integration. `intercom_start_request` already speaks HA device and area ids, so both paths name a target the same way.
3. **A two-way call rings exactly one tablet.** ADR 0025 decision 1 is two peers, and a target that resolves to several devices is ambiguous; it raises `intercom_one_callee` naming them instead of ringing all of them.
4. **Filtering happens before any ring**: capability, then a device already in a call, then the caller's area. A broadcast skips what it cannot use and still runs; a two-way call refuses, because a single skipped target would leave it ringing nobody. If a ring is refused `busy` at the device anyway, that callee is dropped and the caller's side ends with reason `busy`, which is what PROTOCOL 4.5 says.
5. **Timer origins.** The hard limit runs from the moment the call exists (ADR 0002's "answered or not"); the ring limit from the ring; the connect timeout from the answer. A relayed signal in either direction ends `connecting` — HA cannot see ICE, so "the peers are talking" is the best signal it has.
6. **One terminal event per call.** A missed call fires `tabula_intercom_missed` and not `tabula_intercom_ended`, so an automation that notifies about missed calls fires once.
7. **Both id spaces on the bus.** `caller`/`callees` are HA device ids (what a device trigger targets), `tabula_caller`/`tabula_callees` the tablets' TLP ids, the way the relayed device events already carry both.
8. **`intercom_end` raises when there is nothing to end** (an unknown call id, a tablet in no call, both a call id and a target, or neither), following `tabula.notify`'s rule that nothing fails silently. It never raises because a device did not answer the end: the call is over either way, and that is logged.
9. **Timers are HA callback jobs.** `async_call_later` gets a `@callback` target (`_fire`), so the timer, and the `hass.async_create_task` it calls, stay in the event loop; the end work is one task per end. A timer that lands while HA is stopping drops the call instead of scheduling into a stopped loop.
10. **Guard 4 is split in two.** A re-register ends the call for the other side at once; the rejoining tablet is sent `intercom_end` when its subscription is available — right after the subscribe on a new socket, and straight away on a socket that is already subscribed. A non-idle state HA has no call for is logged, not guessed at (see open question 2).
11. **`target_records` now resolves areas through the device registry** as well as through entities, so an area's tablets resolve even when their entities are disabled. Existing services get the same fix, in the direction ADR 0010 item 3 already describes.
12. **A failed ring ends the whole broadcast, on purpose.** Any ring failure other than `busy` ends the call and raises, because a broadcast that quietly lost a receiver would be a failure nobody sees (F-HA-14). Costing every receiver the broadcast when one tablet is unreachable is the conservative half of that trade; a later packet that wants partial broadcasts should change it deliberately, with the event saying who was left out.

### Review (PR #163) fixes

The review at `dc3aee6` asked for one change, one fold-in and two notes; all four are addressed here.

1. **A reused call id is refused, not adopted** (the blocking finding). `async_start_call` raises `intercom_call_id_in_use` when the id is already in `calls`, so a device cannot overwrite a live call's record; the device path logs and drops the request, as it does for every other refusal. `test_a_reused_call_id_is_refused_and_the_live_call_survives` starts a call, has another tablet request the same id for a different target, and proves the first call still rings, still ends on its id, and fires its ended event.
2. **The deferred guard-4 end is drained on a same-socket re-register** (the minor one). `accept_registration` now sends it at once when the session already has a subscription, instead of waiting for a `tabula/subscribe` that may never come; nothing stays queued. `test_same_socket_reregister_mid_call_clears_the_stale_state` proves both tablets get the end and the queue is empty.
3. **The widened area resolution is tested.** `test_intercom_call_by_area_reaches_a_tablet_with_no_live_entities` covers call and end by area with every entity of the tablet disabled, and `test_notify_by_area_reaches_a_tablet_with_no_live_entities` covers the services that gained the same branch.
4. **A failed ring ending a broadcast is recorded as decision 12** above, not changed.

`origin/main` was merged in (P7.2's voice frames added two commands to `COMMAND_CAPABILITIES`; the two hunks sit side by side and the merge keeps both), and `make check` was re-run afterwards.

### Open questions for the architect

1. **An HA-started call cannot reach its own caller's engine.** The callee is rung with the call id, but no v1 frame tells the *caller* its call id, so its engine cannot open a peer connection or send the offer. A call started on the tablet's own screen works (the device chose the id), which is why the relay itself is sound. The fix is a protocol addition — a command that tells a device "you are calling, here is the id", or a ring-to-caller variant — and PROTOCOL is not this packet's to change. Until it is decided, P9.3 can complete device-started calls only.
2. **A stale `intercom_state` that HA has no call for cannot be cleared.** `intercom_end` names a call id and a device acts only on the one it is in, so a tablet that was in a call when HA restarted keeps reporting it until its own limit ends it. Either `intercom_end` gains a "whatever you are in" form, or P9.3's boot guard is the whole answer; the mock and the protocol say the latter is expected, so nothing was invented here beyond the warning. A hub reload has the same shape as an HA restart: `teardown()` drops the calls and sends nothing, so both tablets keep a call HA has forgotten until the device side ends it, which makes P9.3's boot/limit guard the answer for a reload as well as a restart.
3. `INTERCOM_CALL_LIMIT_S` stays **provisional at 300 s**, as P9.1's Result says: the owner confirms or changes it.

Nothing here changes the audio rule: no microphone, no player, and the relayed payload is the peer's own signaling text, copied unread.
