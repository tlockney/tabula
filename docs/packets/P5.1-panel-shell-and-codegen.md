# P5.1 — Panel registration, static bundle and TypeScript codegen

Side: build   Tier: deep   Depends on: none (P1.2, P3.1 and ADR 0001 are merged)
Verification: ci
Issue: #149
Status: in-review

## Why

The Tabularium is a custom HA panel served as a static bundle by the hub entry (plan 5.9). Nothing exists yet: `panel/` holds a README, the integration registers no panel, and only the Kotlin settings classes are generated from the schema. This packet creates the panel's delivery path (Vite + TypeScript + Lit, one ES module with its CSS, a static path and a `panel_custom` registration that is admin-only), the TypeScript settings codegen that every later Phase 5 packet builds on, and the make targets that make the bundle part of `make check`. It deliberately ships only a shell page: the panel proves registration, auth and the panel WebSocket channel without pretending to have data yet.

Panel work is a new language surface in this repository, so this packet also sets the TypeScript conventions (strict, ESLint, Prettier, Vitest) that P5.2–P5.8 follow.

## Do

1. **Panel project.** `panel/` becomes a Vite + TypeScript + Lit 3 app: committed `package.json` and `package-lock.json`; `strict` TypeScript; ESLint (flat config) and Prettier; Vitest with jsdom. Vite builds a single ES module (`panel.js`) with the styles injected by the module (CSS imported `?inline`), target ES2022 for the HA frontend's browser floor, output to `build/panel/`. No runtime dependency outside `lit`.
2. **Bundle delivery.** HA serves files from the component package, so `make panel` builds into `build/panel/` and stages the result into `integration/custom_components/tabula/panel/` (gitignored, never committed). A release is built after `make panel`; document that a source checkout must run `make panel` before installing the integration. The integration logs a clear warning and skips registration when the staged bundle is absent.
3. **Registration.** A new `integration/custom_components/tabula/panel.py` registers the static path (`/tabula_panel`) with `hass.http.async_register_static_paths` and the panel with `panel_custom.async_register_panel`: `url_path="tabularium"`, sidebar title and icon, `require_admin=True`, `embed_iframe=False`, `module_url="/tabula_panel/panel.js?v=<integration version>"` (cache busting; the version comes from `async_get_integration(hass, DOMAIN).version`, which reads the manifest). The manifest's `dependencies` gains `frontend` and `panel_custom`. Registration happens in `async_setup_entry`; `async_unload_entry` removes the panel with `frontend.async_remove_panel` and leaves the static path in place (the HTTP router is frozen, as the existing views are).
4. **Auth.** `require_admin=True` on the panel is not the security boundary: every panel WebSocket command carries `@websocket_api.require_admin`. The panel is a view over the same admin authority as the HA UI; it never receives pairing credentials, tokens or PINs.
5. **Panel WebSocket namespace.** New `integration/custom_components/tabula/panel_api.py`, registered once from `async_setup` like `ws_api.async_register`. Commands are flat and prefixed `tabula/panel_` (`tabula/panel_info` here; later packets add theirs) so the device frame table in `ws_api.py` is untouched and the two namespaces cannot collide. Each command validates its own message shape with voluptuous.
6. **Shell page.** The panel element receives `hass`, renders the panel title and a hub status line from `tabula/panel_info` (integration version, protocol version, settings schema version, paired device count), and a hash route skeleton (`#/devices` is the landing route; the device detail route is P5.2). Styling follows HA's CSS custom properties so light and dark themes work. A visible error state covers a failed `panel_info` call.
7. **TS codegen.** Add a TypeScript target to `tools/codegen.py` (or a sibling `tools/codegen_ts.py`; either way one command drives both targets) that emits the committed `panel/src/generated/settings.ts` from `schema/settings.schema.json`. It must emit:
   - TypeScript types for the whole document (nested objects, enums, nullable types, arrays and objects) and the schema version constant;
   - a runtime `SETTINGS_FIELDS` table in schema order: dotted path and the flat write key (the same `SettingsField.key` the integration uses, e.g. `screensaver_idle_timeout`), role (`identity`/`connection`/`hardware`/`shared`), feature tag, JSON type, enum values, numeric and length bounds, pattern, default (or "no default"), array item kind, and the schema description as help text;
   - `SETTINGS_DEFAULTS` and `SETTINGS_ROLES`.
   It raises on any construct it does not support, exactly as the Kotlin generator does, so a future schema change forces a deliberate update. Output is deterministic. The generated file is committed and gated by drift.
8. **Make targets.** `make panel` (build + stage), `make panel-check` (Prettier check, ESLint, `tsc --noEmit`, Vitest, build), `make codegen-ts`, and `codegen-drift` extended to both languages. `check` gains `panel`; `setup` gains `npm --prefix panel ci`; `fmt` formats the panel sources. CI needs no new step because it runs `make setup && make check`.
9. **Tests.** Python: `integration/tests/test_panel.py` (registration once with the expected arguments when the bundle exists, skipped with a warning when it does not, panel removed on unload, `tabula/panel_info` refused for a non-admin and returned for an admin) and `tools/tests/test_codegen_ts.py` (determinism, drift, unsupported construct raises, every leaf has a role and a feature tag, generated metadata matches the schema's leaf set and order). TypeScript: a Vitest smoke test that mounts the shell with a fake `hass` and asserts the status line and the error state.
10. **Docs.** A "Panel" section in `docs/DEVELOPMENT.md`: Node/npm, `make panel`, where the bundle is staged, the dev loop (`npm --prefix panel run dev` is not used against HA; rebuild and reload instead), and that the bundle is generated and gitignored. Update `panel/README.md` with the stack and the generated file's source.

## Out of scope

- Any real panel page: device list (P5.2), settings (P5.3), logs (P5.4), screenshots and commands (P5.5), profiles (P5.6), updates (P5.7), recovery controls (P5.8).
- A HACS release or packaging pipeline; the staging step is enough until a release task exists.
- Localising the panel; it ships English like the integration's existing UI, with strings in a table the later packets extend.
- Ingress, a separate HTTP server or an iframe-hosted panel.

### Review fixes

The independent review found two blocking items and one minor; all three are fixed
here, each with the test that would have caught it.

1. **The HA matrix was red on all three legs.** Every leg builds its own venv from
   `tools/ha_matrix.sh`, which reads the phacc/ha-ffmpeg/mutagen pins out of
   `integration/pyproject.toml` into a per-leg requirements file, so the
   `home-assistant-frontend` dev pin never reached it and `frontend`/`panel_custom`
   failed to set up. It is now read by the same `pin()` and written into the
   requirements heredoc. Both outer legs were run here, with the bundle staged:

   ```
   == integration tests: pytest-homeassistant-custom-component 0.13.201, HA 2025.1.0, Python 3.13 ==
   176 passed in 18.81s
   == integration tests: pytest-homeassistant-custom-component 0.13.375, HA 2026.10.4, Python 3.14 ==
   176 passed in 17.92s
   ```

   The middle leg is the locked environment `make check` covers below.

2. **`make check` failed once the bundle was built.** aiohttp freezes the router
   when the test server starts; most integration tests start it before loading the
   hub, and setting up the entry is what registers the panel's static path, so the
   registration hit a frozen router (`RuntimeError: Cannot register a resource into
   frozen router`). Production is unaffected: HA's `HomeAssistantHTTP.start()`
   replaces `freeze` with a no-op because components are discovered after boot. The
   `server` fixture now does the same, and
   `test_registers_when_the_server_started_before_the_hub` pins the order that
   fails without it (it errors with the freeze-restoring change reverted). The skip
   test no longer reads the working tree: a `no_bundle` fixture points
   `panel.BUNDLE_DIR` at an empty directory before the hub loads. The packet's
   "Done when" gained the combination that exposed this.

3. **The retry action did nothing.** `retry()` flipped `requested` and called
   `requestUpdate()`, which never re-entered `load()`; it only recovered if HA
   handed over a new `hass`. It now calls `load()` directly, and
   `shell.test.ts` asserts the second `tabula/panel_info` call and that the status
   line replaces the error.

### Deviations

- **The last "Done when" bullet is covered by tests, not by a manual dev-HA run.**
  The packet is `Verification: ci` and this machine runs no HA instance, so
  `integration/tests/test_panel.py` asserts the same three things against real HA
  components through `pytest-homeassistant-custom-component`: the panel is
  registered once with the expected arguments and is served at
  `/tabula_panel/panel.js` (an aiohttp GET returns the staged bundle), it is
  removed on unload and re-registered on setup, `tabula/panel_info` answers an
  admin with the versions and device count, and is refused with `unauthorized`
  for a regular user. What those tests cannot show is a browser rendering the
  element inside a live HA frontend; the Vitest smoke test mounts the shell with
  a fake `hass` under jsdom instead. If the architect wants the manual
  observation recorded, it needs a follow-up task on a machine with a running HA.
- **`panel/package.json` pins exact versions** rather than carets, matching
  `website/package.json`; the lockfile is committed either way.
- **No ADR was needed**: no new tunable constant, no new dependency outside `lit`,
  no divergence from the packet's design.

### Open questions for the architect

- The staged bundle is gitignored, so a HACS install of a checkout has no panel
  until a packaging step exists. That is what the packet asks for ("the staging
  step is enough until a release task exists"), but the release task will have to
  run `make panel` before zipping.
- `module_url` cache-busts on the integration version, so a rebuild without a
  version bump keeps the browser's cached module. `make panel` for a dev loop
  then needs a hard reload; worth a note in the release runbook.
