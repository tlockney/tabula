# P5.7 — Update orchestration

Side: build   Tier: deep   Depends on: ADR 0031 accepted; the Phase 4 packet that lands Shizuku (issue #22); P5.2
Verification: hardware
Issue: #155
Status: blocked

## Why

F-UPD-01 through F-UPD-07 describe self-update: an HA update entity per device, a release source, a package downloaded through HA, verification, the quietest available installer path, progress, a staggered fleet job and an honest "waiting for a tap" state. None of it exists. The installer path is why this packet waits: on Fire OS an ordinary install always needs an on-screen confirmation (F-UPD-05), and the only silent route is the privileged helper that Phase 4's Shizuku work sets up. Building the orchestration first would leave the one thing that distinguishes a good kiosk update — no one walks to the tablet — untested.

The release source is the owner's decision (ADR 0031, proposed). This packet is written against the recommended option (a release folder on the homelab) and keeps the source behind one small interface, so a different answer changes the reader, not the entity, the panel or the device.

## Do

1. **Settings schema v4.** Add the update keys before the code that reads them: `updates.channel` (enum `stable`/`beta`, default `stable`, role `shared`, F-UPD-02) and any installer-path key Phase 4 introduced (the privileged helper's enable switch belongs to Phase 4; reference it, do not duplicate it). Freeze the v3 schema as a copy, bump `schema_version`, extend `migrations.DOWNS` and the Kotlin and TypeScript codegen (both generated files regenerate and are drift-checked), and record the channel set and default in ADR 0002. The channel answers F-UPD-02's open question: per device, `stable` and `beta`, no downgrade.
2. **Release source.** Implement the reader behind one interface (`ReleaseSource`): the ADR 0031 folder layout (manifest, APKs, notes), a configurable path on the hub entry (default `/share/tabula/releases`), tolerant of a missing folder (no releases, a log line, no repair issue), and validating the manifest (schema version, channel, version ordering, per-file sha256, architectures). If the owner chose GitHub instead, only this class changes. Add `tools/release.py` (or a make target) that writes the manifest from a directory of APKs so publishing is one command and the manifest is never hand-edited.
3. **Discovery.** The integration polls the source once soon after start and then at `RELEASE_CHECK_INTERVAL` (ADR 0002), and on demand when HA refreshes the update entity; the device never polls the source (F-UPD-01's open question: the integration queries it, the device only receives commands). Newest release per channel; a release older than the installed build offers nothing; a newer build marks the entity.
4. **Update entity.** A new `update.py` platform: one entity per device that declares the `update` capability, with installed version (from the record), latest version, release notes (optional; offered without notes when absent), `in_progress`, `update_percentage`, and an install action. Availability: the entity stays available while the device is offline (the data is HA's), but install refuses with a clear error. Attributes for the install state (`idle`, `downloading`, `verifying`, `waiting_for_tap`, `installing`, `uncertain`, `failed`) and the reason. A repair issue appears for "update available" and "waiting for a tap" (F-MGT-09) and clears itself.
5. **Transport.** Packages reach devices only through HA: an authenticated download view (bearer token, device resolved from the user, only for that device's pending install, streamed from the release folder with a `UPDATE_MAX_BYTES` bound) returning the package bytes and the manifest's sha256 header. No direct internet access from the device; no new protocol frame.
6. **Device flow.** On `command_update` (with version, URL, sha256, size): download with progress reported as state/attributes, verify size and sha256 and the package's identity and version (refuse another app, an older build, not enough space with the installer's headroom — F-UPD-03 item 4), choose the ABI-matching package or the universal one, then hand over to the installer path: the Phase 4 privileged helper when enabled and authorized (silent), otherwise the system confirmation dialog with lockdown suspended for the install only (F-UPD-06), reporting `waiting_for_tap`; after install, restart the app and reconnect; a lost contact after commit is reported as `uncertain`, never retried automatically. Cancellation works from the device and from HA before the install is committed.
7. **Staggered fleet job.** `tabula.update_devices` (device or area target, optional version): a job that updates devices in bounded batches (`UPDATE_BATCH_SIZE`, ADR 0002), records each outcome (`installed`, `waiting_for_tap`, `failed`, `cancelled`, `uncertain`), emits events and updates the entities; one device waiting for a tap does not block the batch, and the job reports the overall result. The panel's Updates view shows the per-device state, a channel selector per device (schema v4), release notes, per-device install and the job with progress and outcomes. The Tabularium does not invent a second scheduler.
8. **Tests.** Python: manifest parsing (channels, ordering, bad sha, missing files), folder missing/empty, discovery interval and refresh, entity state transitions with a fake source, download view auth/size/expiry/wrong device, job batching and outcomes with an offline and a waiting-for-tap device, repair issue lifecycle, schema v4 migration and translate-down. Mock device: `command_update` through download → verify failure paths and success (no real install), conformance. Android JVM: verification, ABI choice, space check, installer-path selection, progress/cancel, restart-after-install, uncertain handling. Panel Vitest: update states, job progress, channel control, release notes. Schema v4 codegen drift for both languages.
9. **Hardware check.** `tools/device/check_p57.sh` and a `docs/DEVICE.md` runbook: with Shizuku set up, a new release from the folder installs silently and the entity shows the new version; with the helper disabled, the same release waits for a tap and installs after it; a two-tablet job runs in batches and reports each outcome; cancel mid-download leaves the old build; a package with a wrong sha or another app's package is refused before install. Paste the output.
10. **Release runbook.** `docs/DEVICE.md` (or `docs/DEVELOPMENT.md` if it is not device-specific) gets the publishing steps the owner follows: build the APKs, run `tools/release.py`, copy the folder to the share, bump the channel if it is a beta. Keep it to the owner's actual steps.

## Out of scope

- Installing a user-supplied package (F-UPD-09) and the keep-current policy (F-UPD-07's optional part).
- Downgrades, rollback, staged percentage rollouts beyond batching, and update history beyond the current entity state.
- Signing infrastructure changes; the existing release signing stays as it is.
- A GitHub release source other than the adapter named in ADR 0031.
- Anything from Phase 4 itself: the helper, its permission flow and its settings belong to that phase.
