Side: build   Tier: deep   Depends on: P2.1
Verification: hardware
Issue: #16
Status: awaiting-hardware

## Why

The dashboard is the kiosk's main screen. It must authenticate with the device credential without injecting tokens.

## Read first

- `AGENTS.md`
- `docs/PLAN.md` sections 5.8 and 7.3 (P2.2)
- `docs/decisions/0001-ha-platform.md`

## Do

1. Full-screen WebView with external-auth bootstrap, `tabula://` interception and `app://` passthrough.
2. Measure the frontend's background-disconnect behavior and record results in an ADR before writing any shim.
3. Write the hardware check as a script in `tools/device/`.

- The WebView-hiding optimization (Phase 4).

## Done when

- Hardware (pasted by the hardware verifier): the dashboard loads with the device credential; internal links stay in the WebView; screen off/on doesn't reload.

## Hand back

Result section: CI output, background-disconnect ADR number; `awaiting-hardware` when the CI part is done.

### Background-disconnect measurement

ADR **0012** (`docs/decisions/0012-frontend-background-disconnect.md`),
measured before any shim was written, as the packet requires: a local
HA 2026.2.3 with the shipped frontend 20260128.6, driven by headless
Chromium with the V1 bridge injected. The frontend holds its WebSocket for
five minutes of page-hidden, then closes it cleanly (code 1000), and on
becoming visible reconnects to the same page with **no reload and no second
external-auth call**. Decision: no shim; Phase 4's optimization uses the
frontend's own `hass-suspend-when-hidden` lever if the benchmark wants
otherwise. The measurement harness was throwaway (like P0.3's spike) and is
not committed; the method and pasted evidence are in the ADR.

### What was built

- `:ha` — `ExternalAuthBridge` (the frontend's V1 external-auth contract,
  following the Companion app's FrontendJsBridge.kt, Apache-2.0, with
  attribution in the file), `DashboardLinks` (top-level navigation rules:
  same-origin links stay in the WebView, `tabula://action` runs an app action
  without the page navigating, `app://package` opens another app, anything
  else is blocked with a reason; navigate-path resolution and origin checks),
  and `TokenRefresher.accessWithRemaining` (the bridge answers with the
  cached token's remaining life).
- `:app` — `DashboardView` (the full-screen WebView: external-auth bootstrap
  via `addJavascriptInterface`, answers evaluated asynchronously on the main
  thread, main-frame URL tracked for the origin gate, page-finished logging,
  current-page reporting), `DashboardBus` (the service↔activity handle bus),
  MainActivity hosting the dashboard once CONNECTED (it stays loaded across
  CONNECTING blips and is destroyed when the credential fails),
  `TabulaCommands` making `reload`, `clear_cache` and `navigate` real, the
  `navigation` capability declared, `current_page` in the state source, and
  one shared `TokenRefresher` for the session and the bridge.
- `tools/device/check_p22.sh` (the scripted hardware check; also records the
  device WebView version ADR 0001 item 6 is waiting for) and
  `ha_query.py --navigate` (drives `tabula.navigate` from HA over its
  WebSocket).
- PROVENANCE rows for every new user-visible behavior; DEVICE.md gains the
  P2.2 hardware-check section.

### Deviations / decisions

1. **V2 bridge not implemented; V1 only.** ADR 0001 item 3 wants V2 "when the
   server reports 2026.4.2 or later", but TLP v1 carries no HA version to the
   device, so the device cannot evaluate that condition. V1 works with every
   supported HA (ADR 0001), so shipping it alone is the simplest design
   consistent with the ADR; if V2 is wanted, the architect needs to decide
   how the device learns the server version (a claim/register field).
2. **Cross-origin top-level navigation is blocked**, not handed to an outside
   browser: the ADR allowed either, and blocking is the kiosk-safe choice.
   Blocked links toast the reason.
3. **`tabula://` actions are `reload` and `clear-cache` only.** The action
   registry (F-GST-07) and the scheme's manifest registration are Phase 4;
   F-DSH-09 makes restart-app and exit-app not linkable, so they are absent.
   Scheme actions use hyphens (`clear-cache`): underscores are invalid in a
   URL host, which is what the action travels as.
4. **`navigate` and `current_page` implemented although the Do list does not
   name them**: the integration side (P1.3/P1.4) already gates both on the
   `navigation` capability, so the dashboard packet is the natural owner;
   the device now declares it.
5. **The P2.1 on-device "Unpair" button is gone.** The dashboard owns the
   connected screen now and FEATURES has no on-device settings ("settings
   are edited in HA"); unpairing is deleting the device in HA (F-HA-01) or
   `pm clear` (DEVICE.md recovery).
6. **The dashboard URL is the HA root (`$haUrl/?external_auth=1`).** The
   start target (F-DSH-02) is not a settings key yet, so there is nothing to
   honor; when it arrives, it changes the loaded path only.
7. **`clear_cache` clears the WebView cache only, no auto-reload** — reload
   is its own command and button; HA can send both.
8. `check_p22.sh` step 4 approximates "internal links stay in the WebView"
   with a scripted `tabula.navigate` plus a window-focus gate (a navigation
   that handed off to another app fails the check); tapping a real dashboard
   link is left to the verifier's eyeball on the tablet.
9. This Mac's machine-wide uv `exclude-newer` config re-resolves `uv.lock`
   on every local `uv run`; the lock's committed content was restored after
   each run and is untouched in the PR.
