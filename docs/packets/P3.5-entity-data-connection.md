# P3.5 — Entity data connection (subscribe_entities)

Side: build   Tier: deep   Depends on: P3.1
Verification: ci
Issue: TBD
Status: ready

## Why

F-AAG-04: the At a Glance row and the HA-backed widgets subscribe only to their own entities over the device's own HA connection while the screensaver is showing, and unsubscribe when it closes — a dedicated, explicit-list `subscribe_entities` connection, independent of the dashboard page and of TLP. The weather screensaver (P3.7) and the weather/forecast/entity widgets (P3.11) consume the same component. This packet builds that connection: a second HA WebSocket (HA core `/api/websocket`, the same device credential), opened with the screensaver and closed with it.

It also settles how the device reads daily forecast data: HA moved weather forecasts off entity attributes; the current WebSocket API for subscribing to or fetching forecasts must be confirmed against HA core and the Companion app (allowed prior art) and recorded in an ADR before P3.7/P3.11 build on it.

Verification is ci: the component has no visible output; its consumers (P3.6, P3.7, P3.11) carry the hardware checks.

## Do

1. `EntityDataConnection` in `android/ha` (plain JVM): opens a second HA WebSocket with the device credential (token refresh shared with the existing refresher), sends `auth`, then `subscribe_entities` with the explicit entity-id list from settings; holds a state cache; delivers deltas to subscribers. The list is bounded by the schema's bound (P3.1); entities missing from HA arrive as unavailable per F-AAG-03.
2. Lifecycle: opened by `ScreensaverManager` when the screensaver starts (only if the configured mode or overlays need entity data; the black mode's hide-everything option does not open it — F-SSV-06), closed on dismissal; reconnect with bounded backoff while the screensaver shows; a connection that cannot be established leaves the consumers with empty/last-known data, never blocks the screensaver.
3. Forecasts: confirm the current HA WebSocket API for daily forecast data (subscribe or fetch) against HA core; implement the access alongside the state subscription; record the API choice in an ADR.
4. Extend the mock device's test server with an HA-like auth + `subscribe_entities` + forecast path and `/test` hooks to push states, so the JVM tests drive the real client over a real socket (the P2.1 pattern).
5. JVM tests: open/close with the screensaver, explicit list correctness, state deltas, unavailable entities, reconnect during the session, close on dismissal, forecast path, no credential leak into logs.
6. `PROVENANCE.md` rows.
