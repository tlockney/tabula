# P9.1 — Intercom protocol and mock device (signaling)

Side: build   Tier: deep   Depends on: none (ADR 0025, ADR 0028 merged)
Verification: ci
Issue: #139
Status: in-review

## Why

Intercom is the first-priority feature (ADR 0025). Everything after this packet (integration relay, Android engine, screen) needs the wire format first. This packet adds the `intercom` capability to TLP and teaches the mock device to take part in a call without any audio, so the integration side is testable in CI.

## Do

1. Add capabilities `intercom_listen` and `intercom_talk` (ADR 0025 decision 7's concepts; the wire names are single-segment, see the Result's deviation 2) to PROTOCOL 4.0 and 8 as an additive change. No major bump.
2. Define the frames. At minimum: commands integration→device `intercom_ring` (call id, caller device and display name, mode `call` or `broadcast`), `intercom_signal` (call id, `offer`, `answer` or `candidate` payload) and `intercom_end` (call id, reason); device→integration events `intercom_answer`, `intercom_decline`, `intercom_signal`, `intercom_ended` (call id, reason) and `intercom_start_request` (the device asks to start a call from its own screen: target device or area, mode); state key `intercom_state` (idle, ringing, in_call, broadcasting). Use the existing command/result and event shapes; follow PROTOCOL 4.5 rules (one result per command, capability gating).
3. Update `schema/tlp-v1.schema.json`, the integration's bundled copy, golden fixtures in `schema/fixtures/` and `tools/validate_frames.py` coverage, and regenerate the Kotlin codec with `tools/codegen.py` so `android/core` carries the new types. Unknown-enum rules follow PROTOCOL 8.
4. Constants in `docs/decisions/0002-constants.md`: record `INTERCOM_RING_LIMIT_S` = 45 and `INTERCOM_CONNECT_TIMEOUT_S` = 10 (already decided in ADR 0028) and add `INTERCOM_CALL_LIMIT_S`, the hard call limit. Provisional value 300 s (5 minutes); say in the Result that the owner confirms or changes it. Add `INTERCOM_SIGNAL_MAX_BYTES` sized from a real offer SDP (measure one from the spike's saved logs or a synthetic offer; no devices needed).
5. Mock device: declares `intercom_listen`/`intercom_talk` by option, tracks `intercom_state`, answers or declines a ring on command from tests, relays `intercom_signal` events, ends on `intercom_end`, and drops its call on disconnect or restart (guard 4). It carries no audio.
6. Tests: codec round trips, fixtures validate, mock device state machine (ring, answer, decline, ring limit, end, disconnect), conformance test for the capability negotiation (a device that does not declare the capability never receives these commands).
7. `docs/provenance/P9.1.md`: the intercom behaviors are independent design (ADR 0025).

Integration services, entities and the relay (P9.2). Anything in `android/app`. Any real WebRTC.

### Frames

Added to TLP v1 as additive, capability-gated changes (PROTOCOL 8), no major bump:

- capabilities `intercom_listen` and `intercom_talk` (ADR 0025 decision 7 names the concepts; see deviation 2 for why the wire names are single-segment);
- commands `intercom_ring` (`call_id`, `caller_device_id`, `caller_name`, `mode`), `intercom_signal` (`call_id`, `kind`, `payload`) and `intercom_end` (`call_id`, `reason`), all gated by `intercom_listen`;
- events `intercom_answer`, `intercom_decline`, `intercom_signal`, `intercom_ended` and `intercom_start_request` (the last gated by `intercom_talk`, since starting a call needs a microphone), all relayed to one `tabula_intercom` bus event;
- state key `intercom_state` (`idle`, `ringing`, `in_call`, `broadcasting`), where a device playing a broadcast is `in_call` and only the sender is `broadcasting`.

`call_id` has the same form as `command_id` and is chosen by whoever starts the call: the integration for an HA-started call, the device for one started on its own screen. The new `$defs` are `intercom_call_id`, `intercom_mode`, `intercom_signal_kind` and `intercom_end_reason`; `payload` is bounded at `INTERCOM_SIGNAL_MAX_BYTES`.

### Constants (ADR 0002, "Intercom")

| Name | Value | How it was chosen |
| --- | --- | --- |
| `INTERCOM_RING_LIMIT_S` | 45 s | already in ADR 0002 from ADR 0028; recorded in the mock and `:core` |
| `INTERCOM_CONNECT_TIMEOUT_S` | 10 s | same |
| `INTERCOM_CALL_LIMIT_S` | 300 s | ADR 0028 guard 2 requires a hard limit but leaves the value to this packet. 300 s is longer than any across-the-house conversation and short enough that feedback cannot run unattended for an hour. **Provisional: the owner confirms or changes it.** |
| `INTERCOM_SIGNAL_MAX_BYTES` | 4096 B | Measured, not guessed: a synthetic Opus offer of the shape the P9.0 spike logged (`sdpLines=38`, `m=audio ... 111 63 9 0 8 13 110 126`, four extmaps, a sha-256 fingerprint, two SSRC lines) is 1 322 bytes of SDP, or 1 396 once JSON-escaped into the frame; an ICE candidate is about 120 B. 4 KiB is roughly three times the measured offer, admits another codec or extmap, and keeps one relayed frame far under `FRAME_MAX_BYTES`. The measured offer is the `command_intercom_signal.offer.json` fixture, so the bound and the fixture cannot drift apart. |

What the tests cover:

- **Fixtures.** 14 new valid fixtures (three commands, the broadcast variant, two signal kinds, five events, the area target, and `intercom_state` as `ringing`, `in_call` and `broadcasting`) and ten invalid ones, each pinned to the path it must fail at in `invalid/EXPECTED.json`; `register.dotted_capability.json` pins the dotted name as invalid, which is the blocking finding's regression test.
- **Schema enums.** `SchemaEnumsTest` compares every hand-written enum's wire names with the schema's: capabilities, event names, the state, command and event-data enums. It found `go_home` and `illuminance` missing from `Capability`, and would have caught `DismissReason` gaining `busy`.
- **Kotlin codec.** Every fixture decodes strictly and re-encodes unchanged (`TlpFixturesTest`), the three command frames round-trip through their typed args, each event's data round-trips typed, and `IntercomFixturesTest` reads the call id, caller, mode, signal payload and target out of the fixtures. `TlpCodecTest` covers the start request's one-target rule, the payload byte bound, that a capability name stays one segment, and an `intercom_ring` decode.
- **Mock device state machine.** Ring → answer → hard limit; ring → ring limit ("timeout"); decline; a second ring answering `busy`; `intercom_end` with the wrong call id changing nothing; broadcast entering `in_call` with nothing to answer; signals recorded and refused for another call or over the size bound; a reconnect ending the call with `disconnect` and nothing on the next one; `intercom_start_request` target rules; and the three commands NACKing `unsupported_command` on a device that does not declare `intercom_listen`.

### Deviations

Three reviews of PR #160 shaped this. The first found one blocking issue — dotted capability names stop a new device registering with an older integration — and several should-fix points; item 2 is the fix for the blocking one and items 7 to 11 are the rest. The second found two more: the mock sent `intercom_state` without declaring the capability that covers it, and `DismissReason` had gained a `busy` value its schema does not admit (items 12 and 13). Nothing in the frame design, the mock's call state machine or the constant values changed as a result.

1. **The frames were not generated.** The packet's step 3 says to "regenerate the Kotlin codec with `tools/codegen.py`". That tool generates the settings classes only (`Settings.kt`); the TLP codec in `android/core/.../tlp/` is hand-written and has no generator, and P2.0's merged work left it that way. The new types were added by hand and `TlpFixturesTest` is what keeps them honest against the schema. No `codegen` change was invented for it.
2. **The capability names are single-segment, and the register pattern is untouched.** ADR 0025 decision 7 spells the concepts `intercom.listen` and `intercom.talk`; the wire says `intercom_listen` and `intercom_talk`. The first version of this packet widened `register.capabilities` to admit dotted names, and review rejected that as a compatibility break, correctly: `additionalProperties` tolerance does not cover a pattern failure, so an integration older than the loosened pattern rejects the whole `register` frame and the tablet never joins the hub — the exact failure PROTOCOL 4.0 and 8 exist to prevent, in the ordinary "app updated before the integration" order. The v1 pattern is what it was, ADR 0002's bound row says one segment, PROTOCOL 4.0 and 8 state the rule and its consequence, and `register.dotted_capability.json` pins the dotted form as invalid.
3. **The integration relays the events now.** Its `BUS_EVENT_TYPES` table must cover every v1 event, so without the five entries the wire-level conformance run fails with `unknown_error` on `event.intercom_decline` and friends. They map to `tabula_intercom` (the family naming of `tabula_notification` and `tabula_media`), which is what PROTOCOL 4.7 now documents. Services, entities, the call relay, ringing and the screen stay in P9.2 and later, as the packet says.
4. **No timer constant was invented for the mock's deadlines.** The ring limit and the hard limit are checked by `check_intercom_timers()` against the mock's existing injectable clock (the P3.15 pattern), which the unit tests drive; every command checks them too, so a live mock notices on its next one. A background loop would have needed a tick interval that no ADR names.
5. `test_every_command_fixture_is_answered` allows `busy` for `intercom_ring` only, because the fixture set rings the same mock twice; every other command's NACKs stay as tight as before.
6. The two constants ADR 0028 had already chosen were left exactly as they were; this packet only added rows for the two it owns.
7. **`busy` is an `intercom_end` reason.** Review pointed out that a callee refusing a ring because it is already in a call leaves HA ending the caller's side with no honest reason. The enum now carries `busy`, with no other change, and the schema's description says who sends it.
8. **The schema bounds `payload` in characters, the codecs in bytes.** Both descriptions now say so, and PROTOCOL 4.5's row names the byte cap: `maxLength: 4096` is the character bound, `INTERCOM_SIGNAL_MAX_BYTES` the byte bound senders enforce, and the same number covers both for the ASCII SDP and candidates the field carries. Changing the wire to a byte bound would have been a schema change with no gain.
9. **Two more state fixtures** (`in_call`, `broadcasting`) pin every `intercom_state` value end to end, and the Kotlin test reads all three.
10. **Nothing tells a device what to put in `target_device_id` or `target_area_id`.** The frame admits an HA device registry id or an area id, and a device has neither today: `register_result` carries its own `ha_device_id` and no directory. P9.4 step 1 anticipates the directory, so this is its dependency rather than a schema defect, and it is named here so P9.4 does not discover it as one.
11. **The mock's deadlines are documented where they look wrong.** `begin_connection` queues a `disconnect` event before `register` is sent, but the client's event loop starts after registration, so nothing goes out early; and `answer_intercom_call` restarts the call limit at answer time, which is ADR 0002's "from the moment the call is up" rather than ADR 0028's stricter reading. Both now say so in the code.

12. **The mock announces a gated state key only when it declares the capability.** `intercom_state` was in the mock's state for every device, so a device with no intercom capability sent a key PROTOCOL 4.4 covers with `intercom_listen` — and `state` stays strict for unknown keys even in a tolerant receiver, so that key is exactly the one whose presence gets a whole `register` refused. The mock now carries it only when `intercom_listen` is declared, and `test_intercom_is_negotiated_and_commands_are_gated` asserts that no `intercom_*` key appears in an undeclared device's state. PROTOCOL 4.4 also gained the rule in words and its consequence: a gated key reaches a device only in a build that ships after the integration that knows it. Whether 4.4's strictness for unknown state keys should be relaxed — the fix that would remove the ordering requirement — is the architect's call, and P9.2 and P9.3 should not assume either answer until it is made. The mock's `illuminance` has the same shape and the same gate is what 4.4 asks for; it is left as it was, being P3.16's key and not this packet's.
13. **`DismissReason` is back to the schema's four values.** Adding `busy` to `intercom_end_reason` also appended it to `notification_dismissed`'s reason enum, which the schema does not admit: the decoder would have accepted a value whose frames are invalid. Removed. `SchemaEnumsTest` now walks the schema's enums (capabilities, event names, every state, command and event-data enum the codec types) and compares them to the Kotlin `@SerialName` sets, which is the check that would have caught it — and which immediately found the `Capability` enum had been missing `go_home` and `illuminance` since P3.15 and P3.16.

Nothing here changes the audio rule: the mock has no microphone and no player, and the payload is the peer's own signaling text, which HA relays without reading it.
