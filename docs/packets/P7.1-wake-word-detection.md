# P7.1 — Wake-word detection in the production app

Side: build   Tier: deep   Depends on: P7.0   Verification: hardware
Issue: #135
Status: awaiting-hardware

## Why

ADR 0024 puts the wake word on the device and ADR 0029 settles how the Fire HD
10 Plus hears it: `MIC` at 16 kHz mono, no usable echo canceller, half-duplex
detection, microWakeWord's `okay_nabu` on TensorFlow Lite, 6.0 % of one core.
What the spike did not deliver is the feature: detection lives in a separate
debug app (`net.lockney.tabula.spike.voice`), nothing in the production app
runs it, and HA cannot see a detection at all.

The owner wants wake-word detection on one Fire HD 10 Plus ahead of intercom,
because a wake word that fires an HA event is useful on its own: an automation
can dim the screen, stop a timer's tone or announce something without the
assist pipeline existing yet. ADR 0029 also left the accuracy question open
(question 5's clips were never recorded), so this packet has to show the
detector working against recorded audio on the desk before the owner's
scheduled microphone run.

## Do

1. **Setting, schema v3.** A per-device setting `voice.wake_word_enabled`,
   boolean, default `false` (off unless a household asks for it: the microphone
   then runs continuously, which is a decision for the person living with the
   device). Adding a key bumps the settings schema to v3: freeze v2 as
   `schema/settings.schema.v2.json` and the integration's bundled copy, add the
   v3→v2 down-translation, update `SCHEMA_VERSION`, regenerate the Kotlin
   settings, and extend `LEAF_SPEC` and the ADR 0002 table. A `voice` group
   rather than an `audio` leaf, because microphone behavior is not volume.

2. **Protocol.** Three additive, capability-gated changes (PROTOCOL 8):
   - capability `wake_word`;
   - state key `wake_word_active` (bool: the microphone is open and features are
     being computed right now — false when the setting is off, the permission is
     missing or playback has suspended detection). ADR 0029 item 7 requires the
     device to report "no capture" rather than look like it is listening;
   - state key `last_wake_word` (date-time, omit before the first detection per
     4.2's rule for a value that does not exist yet);
   - event `wake_word_detected` with `data` = `phrase` (1–32 chars,
     `[a-z0-9_]+`) and `probability` (integer 0–255).

   Update PROTOCOL 4.2/4.4/4.7 and the TLP schema with valid and invalid
   fixtures for the event and the new state values.

3. **Device core (`android/core`).** A `voice` package with the spike's
   frontend (FFT, 30 ms window, 10 ms hop, 40 mel bins, quantised to the model's
   int8 input range), a `WakeWordModel` interface (so the detector is testable
   without TFLite), and the detector: accumulates feature rows until the model's
   window is full, calls the model, compares against `DETECTION_CUTOFF`, and
   applies `WAKE_WORD_COOLDOWN` so one utterance cannot fire twice. Unit tests
   feed PCM through the frontend and a scripted model through the detector, and
   one fixture test runs a committed 16 kHz WAV through the real frontend.

4. **Device app.** A TFLite implementation of `WakeWordModel` that loads the
   pinned model from the APK's assets. The model file stays out of git (ADR 0029
   item 4): a Gradle task fetches it from the pinned commit, verifies the
   sha256, and copies it into the generated assets directory, so a build needs
   the network once. Capture uses `MIC` with `VOICE_RECOGNITION` as fallback
   (ADR 0029 item 2), starts only while the setting is on, `RECORD_AUDIO` is
   granted and the foreground service runs (service type `microphone`), and is
   suspended while the device plays (ADR 0029 item 3). A detection sends the
   state keys and the event through the existing fan-in.

5. **Integration.** An `event` entity (event types `okay_nabu`), a
   `last_wake_word` timestamp sensor (not diagnostic: it is meant for
   automations), a diagnostic `wake_word_active` binary sensor, the
   `tabula_wake_word` bus event, and a switch for the setting. Entities exist
   only with the `wake_word` capability (F-HA-02) and go unavailable with the
   device (F-HA-04). Tests for each, plus the settings-schema v3 migration.

6. **Mock device.** Declare `wake_word`, report both state keys, and take a test
   hook that emits one detection, so the conformance suite covers the round
   trip. Tests for the hook and the event.

7. **Desk harness.** `make voice-desk`: generates clips with `say -v` (several
   voices, the phrase plus a noise mix) and negative clips (other speech),
   converts to 16 kHz mono with ffmpeg, runs the same model through the
   reference frontend, and prints detections per positive clip and the false
   accepts on negatives. It runs only on macOS with `say` and `ffmpeg`, takes a
   minute, and is not part of `make check`. While building it, fix
   `tools/device/score_wakeword.py`, which divided the reference frontend's
   0–26 features by 25.6 a second time and so scored every clip as a miss.

8. **ADR 0030** for the decisions above (where detection runs, why the event and
   the sensors, the device frontend's limits, the build-time model fetch, the
   half-duplex rule), and **ADR 0002** rows for the new constants.

9. **Owner steps** for the microphone run, in the pull request's Review brief:
   mic only, volume 0, the guard set by the owner, and what to say at 1 m and
   3 m.

## Out of scope

- Streaming audio to HA's assist pipeline (`assist_satellite`, ADR 0024's
  binary channel): a later packet.
- Playback, intercom, announcements triggered by the wake word.
- A user-chosen phrase, or a second phrase: one model, one phrase.
- Echo cancellation. ADR 0029 item 3's half-duplex rule stands.
- Any change to the spike app, which stays as the re-measurement tool.

### Desk harness

`make voice-desk` (macOS `say` and ffmpeg; clips generated at run time, nothing
played, no microphone opened):

```
clip                               kind          s  win  peak hits  verdict
positive-Samantha                  positive    1.6   53   255    1  DETECTED
noisy-Samantha                     noisy       1.6   53   255    1  DETECTED
positive-Daniel                    positive    1.7   54   255    1  DETECTED
noisy-Daniel                       noisy       1.7   54   255    1  DETECTED
positive-Tessa                     positive    1.7   57   255    1  DETECTED
noisy-Tessa                        noisy       1.7   57   255    1  DETECTED
positive-Alex                      positive    1.6   53   255    1  DETECTED
noisy-Alex                         noisy       1.6   53   255    1  DETECTED
negative-0-Samantha                negative    1.8   59    11    0  silent
negative-1-Daniel                  negative    1.8   57    11    0  silent
negative-2-Tessa                   negative    2.3   77    11    0  silent
negative-3-Alex                    negative    1.8   60    11    0  silent
positives detected: 4/4   noisy positives detected: 4/4   false accepts: 0/4
```

Every clip that says the phrase crosses the 200/255 cutoff at least once, with
or without the noise mix; the four ordinary sentences peak at 11/255, which is
the model's silence floor. One detection per clip means the cooldown also held.

The fixed scorer agrees clip for clip (`tools/device/score_wakeword.py`,
`build/desk-clips`, `cutoff=200/255`):

```
negatives: 4/4 miss (peak 11, 0 crossings)
positives and noisy positives: 8/8 hit (peak 255, 16-17 crossings each)
clips with a detection: 8/12
```

The before-and-after ADR 0030 item 9 asks for, on the same twelve clips. The
P7.0 quantiser divided the reference frontend's 0-26 features by 25.6 on top of
the model's own scale, so a one-off probe of those twelve clips with the old
divisor gives:

```
every clip, positives included: peak 10-11/255, so 0/12 could ever cross the
200/255 cutoff
```

That is the "scores every clip as a miss" the tool had: not a model problem but
a scale applied twice. With the single application, the same clips separate
255 from 11.

### What this does not show

The clips are synthesised speech, not the owner's voice in the room, and the
noise mix is flat white noise at a quiet-room level rather than a room's
reverberation, a TV, or the tablet's own speaker. The desk numbers prove the
frontend, the quantisation, the model and the cutoff are wired the way the
device wires them; they say nothing about 1 m and 3 m in the room the tablet
lives in, which is what the microphone run measures.
